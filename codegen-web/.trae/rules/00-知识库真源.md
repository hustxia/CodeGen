# 00-知识库真源（最高优先级规则）

本项目**不在仓库内保存知识库副本**。所有知识与技能只有一处真源，用绝对路径直读：

| 库 | 绝对路径 | 用途 |
|---|---|---|
| 坑库 | `D:/workspace/dev-doc/02-坑/` | 报错、翻车实录、排查过程。按**报错原文** grep |
| 项目速查 | `D:/workspace/dev-doc/01-项目速查/` | 端口、启动命令、代码地图、已知故障 |
| 代码片段 | `D:/workspace/dev-doc/03-片段/` | 可直接复制的 Controller、迁移脚本、配置 |
| 决策记录 | `D:/workspace/dev-doc/04-决策/` | 为什么这么选、当时否掉了什么 |
| 后端知识库 | `D:/workspace/java-backend-knowledge-base/` | 系统性知识：JVM、并发、Spring、MySQL、MQ、微服务 |
| 前端知识库 | `D:/workspace/frontend-knowledge-base/` | 系统性知识：CSS、JS、Vue、工程化、性能 |
| Skills 真源 | `D:/workspace/skills/` | `fullstack-dev`（全栈开发流水线）、`fix-java-bug`（后端排障）、`java-dev-assistant`、`dev-knowledge`（知识库检索/沉淀）。`.trae/skills` 与 `~/.workbuddy/skills` 下均为目录联接 |

## 开发新功能：走 fullstack-dev 流程

新增功能、新模块、新页面+接口，一律按 `D:/workspace/skills/fullstack-dev/SKILL.md` 的十步走：

```
S0 检索 → S1 需求 → S2 数据模型 → S3 功能点 → S4 UI 效果图（用户确认）
→ S5 接口 → S6 后端 → S7 前端 → S8 三层验证（编译/接口/UI 都要证据）→ S9 提交与沉淀
```

三条最容易违反的：**文档不覆盖只追加修订记录**、**效果图没确认不写代码**、**没有验证证据不算做完**。
项目差异（端口、登录 cookie 名、有无 `/api` 前缀）看该技能的 `references/项目适配.md`，不要凭记忆。

## 遇到 bug 的第一步永远是检索

1. 在 `D:/workspace/dev-doc/02-坑/` 用**报错原文** grep（命中率最高）
2. 未命中 → 对应知识库的技术目录（如并发/缓存/构建）
3. 仍未命中 → 才读代码、复现、排查
4. 解决后**必须**把新坑补进坑库

禁止：直接改代码试错、凭记忆给结论。回复里要说明「查了什么、命中没有」。

## 沉淀规则

- **修 bug → 坑库**：症状（贴报错原文）/ 根因 / 解法 / 验证 / 会再遇到，五段式；
  解法必须带**关键代码对照**：❌错误写法 → ✅修复写法，从真实提交摘录并标文件路径。
  只有道理没有代码的条目 = 不合格。
- **方案/设计/新实践 → 知识库对应目录的现有文件**，原地填充「关键代码」段，不新建重复文件。
- 沉淀完提交对应 git 仓库（`dev-doc`、`java-backend-knowledge-base`、`frontend-knowledge-base`、`skills` 均为独立仓）。
- 不要把知识库内容复制回项目 `docs/` 或 `.trae/` 下——同一知识只允许存在一份。

## Skills 改动

只改 `D:/workspace/skills/<name>/` 下的文件。`~/.workbuddy/skills/<name>` 与 `<项目>/.trae/skills/<name>`
都是指向它的目录联接，改一处两端同时生效；这两处不要新建实体副本。
