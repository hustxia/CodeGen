## 一、定位与边界

V9.5 是**「一句话建系统」能力在"建表设计"环节的独立化与增强**，不是新生成器、新部署器，也不是 V9.4 向导的替代品。它与 V9.4 **并列共存**：V9.4 仍是端到端向导，V9.5 是聚焦"AI 推表 + 人确认"的独立模块。

**硬约束（用户指定）：不修改 V9.4 的任何代码。** 所有新增均为"新增入口 + 复用引擎"。

| 做 | 不做 |
|---|---|
| 新增 `/gen/ai-build` 与 `AiTableRecommendService` | 不修改 `GenPipelineController` / `GenPipelineServiceImpl` |
| 复用 `AiModelServiceImpl.model/modules` 做建模 | 不改 `ai-model` / `ai-modules` 既有接口 |
| 复用 `buildDdl`/`prepareDb`/`run` 做落库与构建 | 不新增执行链、不新增部署能力 |
| 复用 `assessRelevance` 相关性护栏 | 不新增 LLM 供应商/配置页面（复用 `gen.pipeline.ai`） |
| 扩展建模 prompt 增加关系/索引/可空 | 不重写解析与白名单清洗 |
| 大型系统服务端分批合并（带进度） | 不改动前端"循环合并"以外的 V9.4 前端 |

## 二、表结构（S2）

### 平台数据库

**无新增表、无新增列、无菜单 SQL。**

AI 推荐表设计在确认落库前是前端暂存或服务端产物文件（`logDir/ai-build/<token>.json`，沿用 `AiRecommendServiceImpl` 的 token 文件范式：`<AB><projectId>-<时间戳>-<hex>`）；确认建库前不产生任何平台或业务 DDL。确认后写入现有 `gen_pipeline`、`sys_project`、`gen_table`、`gen_table_column`。

### 业务数据库

仅在用户点"确认建库"后由现有 `prepareDb` 创建目标库与业务表；若选"落为草稿"，则**业务库零变化**，仅把确认后的表设计导入平台侧 `gen_table`/`gen_table_column`（与 `prepareDb` 的导入逻辑同源）。业务表继续包含 `id`/审计列四件套（由 `buildDdl` 补齐，AI 只管业务列）。

## 三、核心模型

### 3.1 AI 推荐表设计（扩展后，向后兼容现有 `GenPipelineAiVO`）

`GenPipelineAiVO.TableModel` 现有字段：`tableName`、`tableComment`、`columns[{name,type,comment,pk}]`。V9.5 在列与表两层**新增可选字段**，旧 `ai-model` 消费方（V9.4）不受影响：

```json
{
  "tables": [
    {
      "tableName": "asset_info",
      "tableComment": "资产档案",
      "columns": [
        {"name": "asset_name", "type": "varchar(128)", "comment": "资产名称", "pk": false, "nullable": false},
        {"name": "category_id", "type": "bigint",      "comment": "分类",     "pk": false, "nullable": true}
      ],
      "indexes":   [{"columns": ["category_id"], "unique": false, "name": "idx_asset_category"}],
      "relations": [{"column": "category_id", "refTable": "asset_category", "refColumn": "id", "type": "many-to-one"}]
    }
  ],
  "drops": []
}
```

- `nullable` 列级可空（默认 false）；`indexes` 索引建议；`relations` 外键建议。
- 三者均为**建议**：经白名单清洗（外键指向表/列必须存在，索引列必须在表内）后，非法项进 `drops`，绝不写库——复用 `AiRecommendSanitizer` 思路，不在 V9.5 另起一套。
- 类型约束沿用 `AiModelServiceImpl` 既有白名单：`bigint/int/varchar(N)/decimal(M,N)/text/datetime/date/tinyint`。

### 3.2 落库请求

```json
{
  "dbName": "asset_demo",
  "scope": "new",                       // new | supplement（为已有系统补表）
  "projectId": null,                    // supplement 时填已有项目 id
  "tables": [ { "tableName": "...", "tableComment": "...", "columns": [...], "indexes": [...], "relations": [...] } ],
  "mode": "draft"                       // draft（落草稿） | build（直接建库）
}
```

### 3.3 DDL 预览响应

复用现有 `GenPipelineDdlPreviewVO`：`{dbName, ddl, tableCount, statementCount}`——与 `prepareDb` 同源 `buildDdl`，不新增响应结构。

## 四、流程与状态

### 4.1 模块步骤

| 前端 step | 页面 | 主按钮 | 副作用 |
|---|---|---|---|
| 0 | 录入需求 | AI 推荐 | 仅 AI 只读调用（大型先拆模块） |
| 1 | 表设计编辑器 | 确认表设计 | 仅 `previewDdl` 计算 DDL |
| 2 | 落库/建库 | 落为草稿 / 确认建库并构建 | 草稿：导入 `gen_table`；建库：`prepareDb` 进 `await_confirm` |

"为已有系统补表"模式：step 0 选 `supplement` + `projectId`，建模范围限定为该系统缺失的表，确认时只新增、不触碰既有表/列。

### 4.2 状态机（复用 V9.4）

```text
未创建任务（AI/预览阶段）
  │ 选「落为草稿」
  ▼
draft ──（用户后续可在本模块或 V9.4 接管）──► prepare-db ──► await_confirm ──► running ──► success
  │                                                                          │
  │ 选「确认建库」                                                          └──► failed ──► 重试
  ▼
prepare-db 成功 ──► await_confirm ──►（本模块「构建」按钮）──► running
```

任何 AI/预览失败都发生在任务创建前，不产生 `draft/failed` 假任务（与 V9.4 一致）。

### 4.3 大型系统分批编排

```
录入需求（大型）
  └─ ai-modules ──► [M1, M2, ... Mn]
        └─ 逐模块 model(Mi) ──► 进度 1/n, 2/n ...（SSE）
              └─ 按 tableName 去重合并 ──► GenAiBuildPlanVO
```

- 单模块 `model` 输出上限 6-8 张，沿用 `AiModelServiceImpl` 预算控制，本地 7B 不截断。
- 合并：表名冲突首份优先 + `conflicts` 告警；列以表内唯一为准。
- 失败模块：保留成功结果并清单列，不伪造成功（沿用 V9.4 原则）。

### 4.4 几千张表规模设计（用户硬要求：单系统可达数千张表）

> 用户在 V9.5 立项时明确：本模块必须能支撑**一个大型系统「几千张表」的生成**，不能只停留在"≥30 表"的量级。以下为规模化的架构决策，已在交互原型中走查。

**规模预期与拆分**

| 规模档 | 模块数（约） | 表数（约） | 建模策略 |
|---|---|---|---|
| 精简 | 1–3 | <50 | 单模块 `model`，一次出完 |
| 大型 | 10–30 | <500 | `ai-modules` 拆 10–30 模块，逐模块 `model` |
| **超大型** | **150–250** | **2000–5000** | `ai-modules` 拆 150+ 模块，逐模块 `model`，**并发受控**（默认 4–8 并发，受 LLM 连接/速率限制），SSE 双进度（模块级 + 全局表数） |

**服务端规模约束**

1. **产物文件流式合并**：不把全量表设计一次性 hold 在单 JSON 对象里。`<token>.json` 按模块**追加写**，合并时按 `tableName` 去重（首份优先 + `conflicts`）；内存只保留"当前模块结果 + 已合并索引"，避免 3000 表全量 JSON 撑爆堆。
2. **并发编排**：模块建模走有界信号量（默认并发 4–8），失败模块立即记 `drops`/`failedModules` 并继续，不阻塞其余模块、不伪造成功。
3. **DDL 同源但分批**：`buildDdl` 支持"按模块或按 50 表一批"多次调用后拼接，单批 DDL 体量可控（3000 表 ≈ 数 MB，绝不一口气渲染）。
4. **落库分批**：草稿导入（`gen_table`/`gen_table_column`）与真实 `prepareDb` 均按**每批 50 表**切分，顺序/受限并发执行，批次失败可单独重试，避免单事务过大导致锁表或超时。

**前端规模约束（见 §6.1）**

- 模块树（左）+ 表清单（右）双栏；表清单用**虚拟滚动**，3000 行也只渲染可视区。
- 编辑器按**模块作用域**承载，一次只看/编辑一个模块的表；跨模块批量操作（批量设可空 / 批量删）走勾选集。
- DDL 预览按"当前模块 / 全部分块（200 表/块）"切换，并提供"导出全部 DDL 文件"下载，避免一次性渲数 MB。
- 落库页展示"总批次数 / 预估耗时 / 每批 50 表"，二次确认带规模预警。

### 4.5 微服务拆分（部署形态，用户硬要求：生成系统支持拆分，不塞进单一工程）

> 用户明确：生成的系统要**支持微服务拆分**，不能是"所有代码在一个工程里"。V9.5 以 `ai-modules` 拆出的**领域模块**为天然边界——每个模块即一个微服务。

**两种部署形态（step 0 切换；超大型默认微服务）**

| 形态 | 适用 | 代码组织 | 数据库 | 构建 |
|---|---|---|---|---|
| 单体工程 | 精简 / 大型 | 单一后端工程 + 单一前端应用 | 单库单 schema | 构建 1 个应用（沿用 V9.4 范式） |
| **微服务拆分** | **超大型（推荐）/ 大型** | **N 个后端服务工程 + `gateway/` + 前端按模块拆子应用/微前端** | **每服务独立 schema（`dbName_<module>`）或独立库** | 并行构建 N 服务 + 网关，复用 `run` 逐服务 |

**微服务形态的具体设计**

1. **工程拆分**：每个领域模块 → 独立 Spring Boot 工程 `service-<module>/`（controller/service/dao 仅含本模块表）；另生成 `gateway/`（路由按 `/api/<module>/**` 转发）+ 注册中心配置。沿用平台既有部署范式，**不新增部署能力**，复用 `run` 逐服务构建。
2. **数据库边界**：每服务自有 schema；**跨服务不建物理外键**。`relations` 若跨模块，清洗阶段转"逻辑关联"（应用层调用 / 事件），记入 `crossServiceRelations` 展示（不进 `drops`，因仍是有意义的设计，只是实现方式不同）；同模块内关系仍建物理外键。
3. **前端拆分**：按模块拆子应用或微前端（沿用现有 `codegen-web` 生成范式，每模块一个前端工程/路由域）。
4. **构建部署**：流水线从"构建一个应用"升级为"构建 N 服务 + 网关"，沿用现有 `run` 按服务并行构建、各自产物，网关聚合路由。
5. **复用与不触碰**：微服务拆分是 V9.5 `ai-build` 确认/构建路径的**新增编排**——复用 `run`/`prepareDb` 逐服务调用，**不修改** V9.4 向导、`GenPipelineController`/`GenPipelineServiceImpl`（满足 AC-01）。

**对表设计 / 清洗的影响**

- `relations` 增加 `crossService` 标记：跨服务关系不写物理外键，进 `crossServiceRelations`（保留展示），同服务关系正常建外键。
- 编辑器表清单已显示"归属模块/服务"；落库页新增"将生成 N 个微服务"概览（每服务表数 + 自有 schema）。

### 4.6 生成页面规范：隐藏 `id` / 外键列显示关联名称（用户硬要求）

> 用户明确：生成的系统页面**不能出现 `id` 字段**；遇到外键 `id` 字段，**显示关联表对应的名称**而非原始 id 值。这是代码生成模板（产物）的规范，作用于本生成器产出的所有 CRUD 页（列表/详情/表单），V9.4 向导与 V9.5 复用同一套页面模板；**改动的是生成模板与生成逻辑，不是向导组件本身**，不违反 AC-01。

**规则**

1. **主键 `id` 不渲染**：列表页、详情页、表单默认不展示物理主键 `id`（内部字段，对用户无意义）。仅在"超级管理员调试模式"下可开。
2. **外键列 → 关联名称**：列名以 `_id` 结尾且被 `relations` 指向某表 `T` 时，该列在页面上**不显示原始 id 值**，改为显示 `T` 的"名称字段"：
   - 名称字段推断优先级：`T.name` → `T.title` → `T.<实体>_name` → `T` 首个非空字符串列；推断不到则回退显示 `id` 并标黄告警。
   - 页面列标题取外键语义名（如 `category_id` → 列名"分类"），由 AI 注释或字段命名推断。
   - 列表页该列渲染为纯文本名称；**不做**可点击跳转（避免误生成跨页路由），超大型微服务下跨服务 FK 本就转逻辑关联（见 §4.5），更不应暴露 id。
3. **表单中外键 = 关联表下拉**：新增/编辑表单里，外键列渲染为"关联表名称"的下拉选择器（支持按名称搜索、远程分页），**值仍是 id，但用户只选名称**；选项来自关联表，微服务形态下走服务间查询接口。
4. **详情页**：同列表页，主键不显示，外键显示名称；多对一关系展示为"名称（id 隐藏）"。

**实现落点（生成侧，非向导）**

- 页面模板（`Vue` 列表/详情/表单组件模板）新增"列可见性"规则：默认排除 `id` 主键；对 `relations` 命中的 `*_id` 列套用"关联名称"渲染宏。
- 列元数据 `gen_table_column` 增加 `isFk` / `refTable` / `refNameColumn` 推导（复用 V9.5 `relations` 清洗结果），生成器据此决定渲染方式。
- 该规范对**既有生成结果**同样生效（模板统一，重新生成即得新行为）。

### 4.7 生成页面增强：图片上传与富文本编辑（用户硬要求）

> 生成的系统页面需原生支持**图片上传**与**富文本编辑**，不要求用户自己接第三方插件。属于生成模板/脚手架增强，新增到生成产物，**不修改 V9.4 向导组件**（AC-01）。

**规则**

1. **富文本列**：列类型 `text` 或列名命中（`content`/`description`/`detail`/`remark`/`intro`/`body`/`简介`/`详情`）→ 表单渲染为**富文本编辑器**（沿用平台既有富文本组件，如集成 wangEditor/Tinymce）；列表页该列显示"摘要（前 N 字）"或"[富文本]"标记，**不渲染原始 HTML**，防 XSS。
2. **图片列**：列名命中（`image`/`images`/`avatar`/`cover`/`photo`/`pic`/`picture`/`logo`/`封面`/`头像`）→ 表单渲染为**图片上传**组件（单图/多图，支持预览、可选裁剪）；列表页显示缩略图；存储走平台文件服务（复用既有上传/对象存储）。
3. **后端配套**：生成的服务工程自动包含文件上传接口（统一文件服务或 `/api/<module>/file/upload`）；富文本内联图片走资源托管，URL 持久化到对应列。
4. **微服务形态**：文件服务抽为独立 `file-service`（或由网关统一转发），各服务引用同一文件服务，不各自实现存储。

**实现落点（生成侧）**

- 表单模板按列元数据 `widget` 推导：`text`/富文本命中 → `richtext`；图片命中 → `image-upload`；`relations` 命中 → `fk-select`（见 §4.6）。
- 列元数据 `gen_table_column` 增加 `widget` 字段推导（`input`/`richtext`/`image-upload`/`fk-select` 等），生成器据此选择控件。

### 4.8 单表与关联表分离生成 + 主从模板（用户硬要求）

> 生成时需把**单表**与**关联表**分开处理：关联表（存在一对多主从结构）自动识别并配置主从关系，按**主从模板**生成功能模块（主表主列表 + 内嵌明细子表/从表 Tab），而非一律按普通单表 CRUD 生成。属于生成模板/脚手架增强，新增到生成产物，**不修改 V9.4 向导组件**（AC-01）。

**分类规则（在建表推荐产出 `relations` 后、生成前判定）**

- **单表（独立实体）**：无任何外键指向本表（即没有别的表以本表为主表做一对多），或本表自身也无外键 → 走**普通单表 CRUD 模板**（列表 + 新增/编辑表单 + 详情，遵循 §4.6/§4.7 的 id 隐藏、外键显名称、富文本/图片增强）。
- **关联表 → 主从结构**：存在一对多主从关系即拆为**主表 / 从表**：
  - **主表**：被从表外键指向的表（如 `order` 被 `order_item.order_id` 指向）→ 主列表。
  - **从表**：含指向主表外键的表（如 `order_item`）→ 作为主表详情内的**明细子表 / 子 Tab**。
  - 判定：扫描 `relations`，凡外键 `T.fk → M.pk` 且 `M` 为业务主实体（非纯字典表）→ `(M, T)` 组成一对主从。一个主表可带多个从表（一对多），一个从表只归属一个主表（多对一）。
  - **自关联**（如 `category.parent_id → category.id`）→ 视为树形单表模板（树列表 + 层级 CRUD），单列为主从外的第三类，不进主从模板。

**主从模板产出（按 `(M, [T1,T2,...])` 一组生成）**

1. **主表模块**：列表页 + 主表新增/编辑/详情；详情内嵌**从表子区域**（Tab 或折叠区），展示该主记录下的全部从表数据，从表支持行内新增/编辑/删除（明细行）。
2. **从表不单独建菜单**：从表功能挂载在主表详情内，不生成独立左侧菜单项（避免与主表重复），但保留独立 API（`/api/<module>/<detail>/list?masterId=` 等）。
3. **主从联动**：主表选中行 → 右侧/下方明细自动按 `masterId` 过滤；保存主表时支持**级联保存明细**（事务内：主表 insert + 从表明细批量 insert/update/delete 差异）。
4. **级联删除**：删除主表记录时，依据外键约束提示"将级联删除 N 条明细"，默认事务内一并删除（可配置为仅置无效）。
5. **跨服务主从**（微服务形态，§4.5）：主从若跨服务（从表在另一服务的 schema），主从模板降级为**远程关联**——主表详情通过服务间接口拉取明细，不支持事务级联，仅做"逻辑主从"展示，并在模块备注中标明跨服务（沿用 §4.5 的 `crossServiceRelations`）。

**实现落点（生成侧）**

- 在建表推荐/合并阶段产出一个**关系视图** `tableRelations`：`{ tables:[{name, role:'single'|'master'|'detail'|'tree', master?:string, details?:[string] }] }`，生成器据此路由模板。
- 新增**主从模板组**（`masterDetail` 模板族）：主列表 `MasterList.vue` + 主表单 `MasterForm.vue`（含 `DetailTable` 子组件）+ 从表明细行 `DetailRow.vue`。
- 生成器模板选择逻辑：
  - `role==='single'` → 单表 CRUD 模板（现有）。
  - `role==='master'` → `masterDetail` 主模板 + 注入 `details` 列表。
  - `role==='detail'` → 仅生成 API + 明细子组件，不挂菜单。
  - `role==='tree'` → 树形单表模板。
