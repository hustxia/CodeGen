给一所大学画 16 个业务系统的 UI 效果图：智慧校园四层架构 + 524 张表怎么分期落地

场景：一所大学要建智慧校园平台，涉及 SSO 单点登录、统一门户、教务教研、学生服务、OA、人事、采购、档案、资产、维修、能耗、预约、一卡通、物联网、驾驶舱、API 开放平台——16 个系统、估算新增 524 张表。
这篇文章讲的是落地前的全景设计怎么做：四层架构怎么分层、16 个系统怎么分期、UI 效果图先画给谁看、每个系统按什么 SOP 落地。文中的 UI 效果图是按生成器真实产出风格绘制的高保真设计稿（HTML），用于立项汇报与开发对齐。

一、接到需求的第一件事：分层，不是开写

16 个系统一股脑开工必死。第一步是按职责分层，让"谁先行、谁后行"一眼可见：

层 定位 系统数 新增表估算 说明
基础支撑层 全校底座，先行 6 ~77 表 SSO / 门户 / 一卡通 / 物联网 / 消息总线 / 移动端
业务应用层 价值主体，批量复制 10 ~313 表 + 复用 66 教务教研、学生服务、OA、人事等
治理与决策层 数据汇聚，后行 7 ~119 表 驾驶舱 BI 等，依赖前两层业务数据
开放生态层 能力输出 1 ~15 表 API 开放平台

合计约 524 张新表 + 复用 66 张（人才培养方案系统）+ 15 张通用表。对照智慧村务（85 表当天落地）的实测节奏，总量在代码生成器能力范围内——但必须分期。

三条落地原则

  1. 一域一系统：按业务域独立建库（campus_sso、campus_oa、campus_bi……），不合并成单体。12 步流水线按项目跑，60~80 张表/库是最佳粒度，超过 100 张菜单和验收都会变重。
  2. 底座先行，数据后聚：一期先把账号/组织/消息做统一，业务系统全部挂底座；治理层只在四期启动——避免"没数据先建中台"的空转。
  3. 已验证 SOP 全程复用：每个系统走同一条流水线，前几个系统踩过的坑（枚举三件套、菜单同源）已在模板层修复，新系统不重交学费。

二、效果图为什么先画：给两个对象看

写代码之前，先给 16 个系统各画一张核心页面的高保真效果图（浏览器窗框 + 侧边栏 + 顶栏 + 业务区的完整布局）。这是给两类人看的：

  1. 校方领导：立项汇报要"看得见"。一张登录页 + 一张业务看板，胜过十页 PPT
  2. 开发自己：效果图即 UI 契约。布局按生成器真实产出的风格画（Element Plus 组件体系、统计卡 + 工具栏 + 表格 + 状态标签），落地时生成的页面和设计稿天然对齐，不会出现"设计稿一个样、生成出来另一个样"

设计规范要点

  • 布局骨架统一：左侧 178px 侧边导航（分组菜单 + 高亮项）、顶部 44px 面包屑栏、内容区按业务类型套用四种模式——统计卡看板、工具栏列表页、步骤条流程页、日历/预约视图
  • 配色克制：主色 #409eff，成功/警告/危险用 Element 标准色，大屏用深色渐变
  • 每个系统只画一张"最能代表它"的页面：登录画登录页，管理画列表页，监测画看板，审批画看板流，驾驶舱画大屏

效果图里值得学的一页：能耗监测

以能耗系统为例，看效果图的"信息密度"怎么设计（这些数字都是按真实业务口径编的演示数据）：

  • 顶部统计卡：本月用电 18.6 万 kWh（同比 -4.2%）、3 条异常告警待确认、486 块联网表计
  • 分区占比：教学区 7.2 万 kWh · 39%｜实验区 5.8 万 · 31%｜学生生活区 4.1 万 · 22%｜公共 1.5 万 · 8%
  • 异常清单（直接给结论而不是裸数据）："S305 机房夜间基线异常，较上周 +38%，疑似空转"；"金工中心功率因数 0.82（标准 0.9），待整改"
  • 表计在线状态：分区域在线率 + 最近抄表时间

汇报时领导一眼看懂"电用在哪、哪里有问题"；开发拿到页面就知道统计卡要哪几个接口、异常清单查哪张表。效果图的信息结构 = 后端的接口清单，这是它最大的工程价值。

四、从效果图到真实系统：对齐生成器而不是手写

设计稿确认后，每个系统走同一条已验证的 9 步 SOP：

S1 功能设计文档（域锚定 + 表级清单）
S2 tables JSON（业务表字段内嵌 + 15 通用表标配复制）
S3 校验（--check-labels + 模板护栏）
S4 流水线 12 步（ddl-preview 一致性 → create → prepare-db → 生成）
   —— 60 表规模实测约 7 分钟
S5 菜单重规划（业务域三级结构，路由与菜单同源）
S6 页面级后处理（枚举收敛 + 关联下拉 + 悬空外键清理）
S7 演示数据（真实业务口径灌库，幂等可重跑）
S8 三层验收（前端 build ✓ + 后端 compile ✓ + 逐页截图 console 0 错误）
S9 沉淀（坑库补缺 + 增长钩子 + 实战文）

单系统节奏参照已落地系统的实测：设计建模半天 + 流水线后处理半天 + 数据验收半天，约 1.5~2 人日/系统；全案 16 系统约 25~30 人日，四期 6~8 周可完成。

五、跨系统的五个关键决策（返工都返在这里）

多系统最大的坑不在单系统内部，而在系统之间：

决策点 方案
统一登录 SSO 是账号真源，其余系统令牌校验接入；一期先共享登录态，二期升级标准 OIDC/JWT
跨系统待办 门户的待办聚合表存各系统审批回执（异步推送），不做跨库实时 join
外键跨库 不建跨库外键，跨系统引用存"系统标识 + 业务单号"，展示由门户聚合
编码标准 组织机构、工号、资产编码在数据标准里先锁定，避免中台期返工
演示数据 每系统一个幂等可重跑的种子脚本，主线数据按真实口径

六、风险清单（全部来自已踩坑记录）

  1. 枚举三件套不收敛 → 已在模板层修复；新系统仍须 build + 逐页截图断言 console 0 错误
  2. 业务枚举错配通用映射 → 后处理完跑一次枚举误指检查
  3. AI 菜单推荐对自定义表返回空 → 一律手动菜单重规划，不依赖 AI 推荐
  4. 后处理后忘重新打包 → 验收清单第一条：jar 时间戳 vs 源码时间戳
  5. 巨型单体诱惑 → 严格一域一库，任何单库超 100 张表即触发拆分评审

这五条没有一条是理论风险——都是前面九个落地系统真实撞过的墙，直接写进每个系统的验收清单。
