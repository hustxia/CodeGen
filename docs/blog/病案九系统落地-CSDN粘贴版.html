病案系统群怎么落地：9 个医疗系统的四层分期、表结构设计与代码生成器 9 步 SOP

场景：一家医院要建病案与医疗质量系统群，需求清单有 9 个系统——病案管理与统计、病案首页质控、病案示踪管理、病案无纸化管理、病案数字化翻拍、无纸化病案归档、医疗质量管理、病历质量管理、医院感染管理。

这篇文章讲的是多系统医疗项目的落地全景设计：9 个系统怎么分层、哪几个先行、单库表数怎么控制、跨系统的主键与编码怎么统一、每个系统按什么 SOP 交给代码生成器。核心观点只有一句：病案系统的难点不在单个页面的 CRUD，而在系统之间的边界。

一、接到需求的第一件事：分层，不是开写

9 个系统一起开工必死。第一步是按数据依赖分层，让"谁先行、谁后行"一眼可见：

层 定位 系统 表规模 说明
一期 · 底座层 共享服务，先行 统一认证/科室人员、患者主索引、ICD 编码字典、对象存储与审计 15 张通用表 + 共享字典 所有业务系统挂底座，编码标准先锁定
一期 · 核心业务层 先打样，走通主链 病案管理与统计、病案示踪管理、病历质量管理 三库各 40~70 表 建案 → 流转 → 质控，一条主线跑通
二期 · 采集归档层 影像链路 病案数字化翻拍、病案无纸化管理、无纸化病案归档 三库各 30~60 表 影像放对象存储，库里只存 URL 与页码
三期 · 质控决策层 规则与统计，后行 病案首页质控、医疗质量管理、医院感染管理 三库各 30~60 表 依赖前两期的病案首页与归档数据

合计约 400~500 张表 + 15 张通用表。对照已落地系统的实测节奏（智慧村务 85 表当天落地、人才培养方案 66 表流水线 7 分钟生成），总量在代码生成器能力范围内——但必须分期。

三条落地原则

  1. 一域一系统：按业务域独立建库（mr_core、mr_trace、mr_scan……），不合并成单体。12 步流水线按项目跑，50~70 张表/库是最佳粒度，超过 100 张菜单和验收都会变重。
  2. 底座先行，质控后行：一期先把患者主索引、住院号、ICD 编码字典统一，业务系统全部挂底座；质控与统计放三期——避免"没数据先建质控"的空转。
  3. 已验证 SOP 全程复用：每个系统走同一条流水线，前面系统踩过的坑（枚举三件套、悬空外键、菜单同源）已在模板层修复，新系统不重交学费。

二、九个系统逐一定位：代表表与生成要点

不要一上来就画 9 套页面。每个系统先定"最能代表它的那张表 + 那个页面"，再进流水线：

系统 代表表（举例） 生成与后处理要点
病案管理与统计 病案主表、病案首页、就诊索引、统计口径 以住院号/就诊号为业务主键；患者主索引在底座统一
病案首页质控 规则定义、质控批次、问题明细、申诉复核 规则元数据入库，规则执行器外置适配器
病案示踪管理 示踪单、流转节点、条码、借还登记 状态枚举密度高，S6 枚举收敛必跑
病案无纸化管理 无纸化申请、电子签名记录、结构化录入 CA/签名走适配器，生成器只做 CRUD
病案数字化翻拍 翻拍批次、影像页、质检记录 影像存对象存储，库里只存 URL + 页码
无纸化病案归档 归档目录、归档卷、借阅、销毁审批 生命周期状态机 + 保留期字段
医疗质量管理 指标定义、监测记录、质控台账 指标计算外置，生成器做配置与结果展示
病历质量管理 环节质控、终末质控、评分、整改闭环 与首页质控共用规则元数据表，不重复造
医院感染管理 感染病例、暴发预警、耐药监测、消毒记录 预警算法外置；枚举后处理 + 悬空外键清理必跑

看过九个系统的表清单会发现一个规律：真正需要代码生成器做的只有三类东西——基础档案、业务单据、流程台账。评分算法、预警模型、影像存储、电子签名全部是外部适配器。接受这条边界，项目才不会烂尾。

三、跨系统五个决策：返工都返在这里

多系统最大的坑不在单系统内部，而在系统之间。这五条必须在开工前定案：

决策点 方案
统一编码字典 ICD-10 / ICD-9-CM-3 / 国家临床版带版本号放底座，9 个系统只读引用，绝不各自复制
跨库外键 不建跨库外键，跨系统引用存"系统标识 + 业务单号"，展示由门户聚合；不做跨库实时 join
统一登录 SSO 是账号真源，其余系统令牌校验接入；一期先共享登录态，二期升级标准 OIDC/JWT
计算边界 质控评分、院感预警、统计指标、排程一律适配器外置，生成器不做计算
隐私与安全 种子数据全部脱敏；字段级权限 + 全量审计日志 + 限流，医疗数据不能只靠"登录可见"

其中隐私与安全是医疗项目比校园/企业项目多出来的一条红线：演示数据必须脱敏，患者姓名、身份证、住院号在生产环境要有字段级权限，并把访问控制与审计日志做成底座服务，而不是每个系统各写一遍。

四、单系统 9 步 SOP（与前几个落地系统同源，全部复用）

S1 功能设计     —— 域锚定 + 代表表清单（先定"最能代表这个系统的页面"）
S2 tables JSON  —— 业务表字段内嵌 + 15 张通用表标配复制
S3 校验         —— --check-labels 校验关联配置 + 模板护栏
S4 流水线       —— ddl-preview → create → prepare-db → 12 步（60 表 ≈ 7 分钟）
S5 菜单重规划   —— 按业务域三级结构重写路由与菜单（路由菜单同源）
S6 页面级后处理 —— polish_enums_refs + 悬空外键清理（医疗状态枚举密度极高，必跑）
S7 演示数据     —— 脱敏种子脚本，按真实业务口径（一条病案从建案到归档的主线）
S8 三层验收     —— 前端 build ✓ + 后端 compile ✓ + 逐页截图 console 0 错误
S9 沉淀         —— 坑库补缺 + CSDN 实战文一篇

单系统节奏参照已落地系统的实测：设计建模半天 + 流水线后处理半天 + 数据验收半天，约 1.5~2 人日/系统；全案 9 系统约 18~25 人日，三期 4~6 周可完成。

五、医疗场景特有的五个坑（前面九个系统真实撞过）

  1. 巨型单体诱惑：9 个系统看着像"一个病案平台"，但绝不是一个库——任何单库超 100 张表即触发拆分评审。
  2. 业务枚举错配通用映射：医疗系统的状态枚举远多于校园（示踪状态、质控结论、归档阶段、感染分类……），页面级后处理必须 grep 复查非 status 字段误指通用 enumText('status')。
  3. 悬空外键井喷：人才培养方案系统实测 861 条悬空引用全靠 --fix-dangling 清理；病案单据行表外键只多不少，S6 必跑且验收时 grep 复查。
  4. 把计算塞进生成器：质控评分、院感预警必须适配器外置。生成器做的是"可编译可运行的骨架 + 配置页面"，不是算法引擎。
  5. 后处理后忘重新打包：验收清单第一条——jar 时间戳 vs 源码时间戳；医疗项目验收周期长，最容易在这里翻车。

  • [ ] 每系统一张代表页效果图（布局 = 生成器模板布局，避免设计稿与产出不一致）
  • [ ] 表数估算：单库控制在 50~70 张，15 张通用表复制清单明确
  • [ ] 跨系统决策五件套（编码/外键/登录/计算边界/隐私）先定案再开工
  • [ ] 种子数据脱敏，生产环境字段级权限与审计日志在底座实现
  • [ ] 每系统走 9 步 SOP，验收 DoD 不打折
  • [ ] 单库超 100 表 → 拆分评审

如果只选一个系统打样，选病案管理与统计：它是其余 8 个系统的主数据来源（患者、就诊、病案首页），先把主索引和首页建模跑通，示踪、质控、归档才有挂靠对象。顺序建议：一期底座 + 病案管理与统计 + 病案示踪 + 病历质量（走通一条"建案 → 流转 → 质控"主链），二期影像链路三系统，三期质控决策三系统。
