智慧校园管理系统怎么落地：9 大业务域 61 张表的建模拆解 + 12 步流水线生成，附 5 个真实踩坑

校园信息化是最典型的"表多、域多、角色多"场景：招生迎新、学籍、排课、成绩、宿舍、一卡通、门禁、请假、离校，一个完整智慧校园平台轻松超过 50 张表。
这篇文章给一条可以直接照做的落地路径：业务域怎么拆、表怎么建模、代码生成器 12 步流水线怎么跑、菜单权限怎么规划，最后附 5 个我们系列实战里真实踩过的坑（都在后台日志里留下过现场）。

一、为什么智慧校园特别适合代码生成器

先说结论：智慧校园是 CRUD 密度最高的场景之一，手写不划算。

一个中等规模学校的信息化平台，绕不开这些现实：

  • 表多：学生、教师、班级、课程、宿舍、床位、卡账户、消费流水、门禁记录、缴费订单……业务表 40 张起步，加上用户/角色/菜单/字典/日志这些通用表，60 张很正常
  • 角色多：教务处、院系管理员、辅导员、宿管、财务、学生，同一张表不同角色看到的字段和按钮都不一样
  • 变更剧烈：每年迎新季、评奖季、离校季，流程和字段都会改，手写系统改一次表要动 Controller、DTO、VO、Vue 页面、菜单 SQL 五个地方
  • 痕迹要求高：门禁、请假、消费都要留痕，审计字段和逻辑删除是标配

这些特点指向同一个结论：** schema 定下来之后，80% 的代码是机械劳动**——正是代码生成器的主场。

二、先划边界：它和人才培养方案系统管的事不一样

动手建模前先对齐口径，避免两套系统重复建设：

智慧校园（本篇） 人才培养方案系统（系列前作）
管什么 学生在校全过程：迎新 → 学籍 → 排课 → 成绩 → 宿舍 → 卡务 → 门禁 → 请假 → 离校 教什么：培养目标、毕业要求(OBE)、课程体系、学分结构
核心实体 学生、宿舍、校园卡、门禁记录 培养方案、毕业要求、课程地图
变更频率 每学期/每月都在变 每年大改一次

边界定了：课程库、教学班这种两边都要用的基础数据，在智慧校园里只做引用，不重复建模。真实项目里这就是两个子系统共享一个基础数据域。

三、建模：9 个业务域，61 张表

拆域的原则还是那两条：一张表管一件事、域内高内聚域外低耦合。智慧校园拆成 9 个业务域 + 1 个系统域：

业务域 覆盖内容 代表表
基础数据 校区、学院、专业、班级、学年学期、教师 cam_campus / cam_college / cam_class / cam_academic_term
学籍管理 学生档案、学籍注册、学籍异动（休学/复学/转专业/退学） cam_student / cam_enroll / cam_status_change
教务排课 课程库、教学班、课表、调停课申请 cam_course / cam_teaching_class / cam_schedule / cam_schedule_change
考试成绩 考试安排、成绩录入与审核、补考重修、绩点规则 cam_exam / cam_score / cam_resit / cam_gpa_rule
请假考勤 请假申请（走审批流）、考勤签到、异常考勤处理 cam_leave_request / cam_attendance / cam_attendance_abnormal
宿舍管理 楼栋/房间/床位、分配与调宿、卫生检查、报修 cam_dorm_building / cam_bed / cam_dorm_assign / cam_repair
一卡通与缴费 卡账户、充值、消费流水、缴费项目与订单、退款 cam_card_account / cam_card_txn / cam_pay_item / cam_pay_order
门禁通行 门禁设备、通行记录、黑名单管理 cam_gate_device / cam_gate_log / cam_gate_blacklist
离校与就业 离校手续单、各部门核销、就业去向登记 cam_leave_school / cam_leave_item / cam_career
系统管理 用户、角色、菜单、字典、日志、通知、任务、附件 15 张通用表

合计 46 张业务表 + 15 张通用表 = 61 张。

两条建模铁律

铁律一：字段注释全中文。 生成页面的 label 直接来自字段注释，注释质量 = 页面质量：

-- ❌ 错误：注释是给开发看的
`status` tinyint COMMENT '状态',

-- ✅ 正确：注释是给用户看的，枚举值写全
`status` tinyint COMMENT '学籍状态:1=在读,2=休学,3=复学,4=转专业,5=退学,6=毕业',

铁律二：外键字段全部可译。 major_id 这种技术字段名出现在页面上就是事故，配好"字段 → 中文标签"映射词库后，生成器会把 major_id 翻译成"所属专业"，列表页自动做关联翻译。

三个容易漏的设计点

  1. 床位表不要省：很多人宿舍建模只到"房间"，但调宿、卫生检查、门禁联动都以床位为粒度，cam_bed 一张表省不得
  2. 消费流水与卡账户分离：账户存余额，流水存每一笔，余额永远由流水可推导——审计和 troubleshoot 都靠这个
  3. 审批类表（请假、调宿、调停课）统一走同一套审批结构：生成器支持工作流能力包，审批单/节点/意见三张表的结构保持一致，后面前端和权限都能复用同一套模式

四、生成：12 步流水线

61 张表的 DDL 按 9 个域整理成脚本后，剩下的交给流水线：

登录 → DDL 预览 → 建库建表 → 项目创建 → 环境自检
→ 后端生成 → 前端生成 → 菜单生成 → 打包 → 部署 → 健康检查 → 完成

几个值得说的细节：

  • DDL 预览与实际建库做一致性校验，字段类型、长度问题在生成前就暴露，不会等到运行时 500
  • 建库分批执行：61 张表的 DDL 一次提交容易超时，生成器支持 db-batch-size（默认 50）自动分批，每批独立提交，失败时直接报批号和摘要，定位很快
  • 每一步有独立的失败原因记录（failReason），重跑不会残留上次的失败状态
  • 生成产物是一个完整工程：后端 Entity/Mapper/Service/Controller/DTO/VO + Vue3 页面 + 路由 + 菜单 SQL，编译自检通过才算成功

生成完成后的验收口径和系列前作一致：零空列表、零页面错误——每一页都点开看过，菜单树全部可达。

五、菜单与权限：三级结构 + 五个角色

61 张表生成的页面默认平铺，直接给用户看没法用。按惯例重排成三级：

一级：智慧校园管理系统
  ├── 业务域：学籍管理 / 教务排课 / 考试成绩 / 宿舍管理 / 一卡通缴费
  │           门禁通行 / 请假考勤 / 离校就业 / 基础数据（共 9 个）
  └── 三级：功能页面（每域 3~6 页）

然后按角色裁剪可见性，这是智慧校园区别于其他场景的重点：

角色 能看到什么 典型操作
教务处 全部教务/成绩/学籍域 成绩审核、学籍异动审批
辅导员 本班学生学籍、请假审批、宿舍分配 审批请假、查看异常考勤
宿管 宿舍域 卫生检查、报修派单
财务 缴费域 退款审核、缴费对账
学生 自己的课表/成绩/宿舍/卡余额 提交请假、在线缴费、报修

生成的按钮权限是按页面自动铺的（每页查询/新增/编辑/删除/导出五件套），角色配置时只需要按上表勾选业务域，不需要手工逐页配。

六、演示数据：让系统"看起来在运行"

空系统给领导演示是没有说服力的。生成后用种子数据灌入贴近真实的口径：

  • 3 个校区、12 个学院、40 个专业、200 个班级
  • 5000 名学生的学籍档案（姓名、学号、学院专业班级、宿舍床位一一对应）
  • 一学期课表、成绩分布（正态）、消费流水（食堂三高峰）
  • 门禁记录覆盖宿舍晚归、上课缺勤等异常场景

生成器的 AI 种子增强会按字段注释理解业务含义来造数据，注释写得越好，演示数据越像真的——这又回到了铁律一。

七、5 个真实踩坑（都在我们系列实战里留过现场）

以下坑不是理论推演，全部来自 CodeGen 系列系统的真实翻车记录，都修过、验证过。

坑 1：业务编号用秒级时间戳拼，同一秒连建两条必撞唯一键

现象：缴费单号 = 前缀 + yyyyMMdd + 秒级时间戳，测试时手工快速连建两条，Duplicate entry 报错。

uk_no 冲突：PAY20261115093012 已存在

根因：秒级时间戳的粒度是 1 秒，同一秒两条记录编号必然相同。

修复：时间戳到毫秒，再拼一段随机尾：

// ✅ 前缀 + 毫秒时间戳 + 4 位随机尾
String no = "PAY" + System.currentTimeMillis() + RandomUtil.randomNumbers(4);

校园场景里所有单号（缴费单、报修单、请假单）都适用这一条。

坑 2：逻辑删除列进唯一索引，第二次删同一业务键必撞

现象：学号 uk_student_no 唯一，学生退学（逻辑删除）后，同号复学再录入，Duplicate entry。

根因：唯一索引只有业务列，被逻辑删除的行还占着唯一键位置。

修复：唯一索引带上删除标记，或删除时改写业务键（如追加删除时间戳）。智慧校园里学号、卡号、手机号这三类"看起来该唯一"的字段都要过一遍这个检查。

坑 3：19 位雪花 ID 返回前端精度丢失

现象：列表页点详情，查的是 ID 2112438959048089602，后端收到的却是 2112438959048089000——查不到任何数据。

根因：JS 的 Number 只有 53 位安全整数精度，19 位雪花 ID 传到前端再传回来就变了。

修复：ID 字段序列化时统一转字符串返回（Jackson 配置 Long → String），前端全程按字符串处理。生成器默认配置已带这一条，但自己手写的接口别忘了。

坑 4：脱敏占位符按"前缀 + 雪花 ID"拼，长度炸穿 varchar

现象：学生手机号脱敏存储后，偶发写入报"Data too long"。

根因：脱敏占位符的拼法是"前缀 + 完整雪花 ID"，19 位 ID 加前缀超过了 varchar(20) 的列宽。

修复：脱敏占位符的长度必须按目标列宽反推，或者干脆放宽列宽。校园里身份证号、手机号、家庭住址都是脱敏高频字段，建表时就把列宽留足。

坑 5：实体加了字段，迁移脚本没写——开发库手工 ALTER 过，换环境就炸

现象：开发环境一切正常，部署到演示环境，启动即 Unknown column 'bed_id' in 'field list'。

根因：开发时图快直接在数据库手工加列，代码里的实体同步加了字段，但迁移脚本（DDL 版本文件）没写——环境一换就现原形。

修复：立规矩——实体字段的任何变更，必须同步出现对应的 DDL 迁移文件，靠代码评审抓，也靠"空库冒烟"兜底（每次发布前用干净空库跑一遍全部迁移脚本）。

八、落地检查清单

把这篇的方法压缩成一张清单，照着走：

  • [ ] 业务域拆分 ≤ 10 个，每个域 3~6 张表，一张表管一件事
  • [ ] 字段注释全中文，枚举值写全；外键字段配好翻译映射
  • [ ] 流水与账户分离（余额可由流水推导）
  • [ ] 审批类业务复用同一套审批表结构
  • [ ] DDL 分批参数确认（表多 > 50 时必看）
  • [ ] 菜单三级重排，按角色裁剪可见性
  • [ ] 种子数据灌真实口径（注释质量决定数据质量）
  • [ ] 验收口径：零空列表、零页面错误
  • [ ] 发布前空库冒烟：干净空库跑通全部迁移脚本
