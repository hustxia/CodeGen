# 给一家制造企业画 20 个业务系统的 UI 效果图：ERP/CRM/MES 缩写密集型全景怎么分期落地（约 520 张表）

> 场景：一家制造企业要上企业级信息系统，涉及 ERP（财务/供应链/生产）、CRM、OA/BPM、HRM、费控、PLM、MES、SCM/SRM、WMS、TMS、QMS、APS、SCADA、BI 数据中台、CLM、GRC、DMS、OMS——20 个系统、估算新增约 520 张表。
> 企业系统和智慧校园最大的不同：**缩写密集**。每个缩写（ERP/CRM/MES/WMS…）背后是一个独立系统、一套独立库，拆不好就是 600 张表的巨型单体。这篇文章讲的是全景设计怎么做：缩写怎么拆库、20 个系统怎么分三期、UI 效果图先画给谁看、跨库单据链怎么追。文中的 UI 效果图是按生成器真实产出风格绘制的高保真设计稿（HTML），用于立项汇报与开发对齐。

## 一、接到需求的第一件事：拆缩写，不是建单体

企业系统的第一陷阱是"ERP 是一个词，所以 ERP 是一个系统"。实际拆下来，光 ERP 一个缩写就含三个子域：

- **财务**（科目/凭证/账簿/应收应付/期末结转，约 25 表）
- **供应链**（物料主数据/采购/销售/库存台账，约 35 表）
- **生产**（生产订单/BOM 展开/领料/完工入库，约 30 表）

三个子域加起来就 90 张表。如果塞进一个库，任何一次页面生成、一次 schema 变更都要扛着 100+ 张表跑。所以第一条原则是：

**一缩写一库，ERP 虽是一个词也拆三库**（`erp_fin` / `erp_scm` / `erp_prod`），单库控制在 50~70 张表——这正是代码生成器 12 步流水线的最佳粒度。

### 三大类拆解全景

| 类别 | 定位 | 系统数 | 新增表估算 | 系统清单 |
|---|---|---|---|---|
| 核心经营类 | 经营主线，先行 | 5 | ~220 表 | ERP·财务、ERP·供应链、ERP·生产、CRM、OA/BPM、HRM、费控/EPM |
| 研产供与物流类 | 价值链主体，批量复制 | 8 | ~230 表 | PLM、MES、SCM/SRM、WMS、TMS、QMS、APS、SCADA |
| 支撑与治理类 | 数据汇聚与合规，后行 | 5 | ~108 表 | BI/数据中台、知识文档 CLM、GRC/内控审计、DMS、OMS |

合计约 **520 张新表 + 15 张通用表**。对照已落地系统的实测节奏（智慧村务 85 表当天落地、人才培养方案 66 表流水线 7 分钟生成 + 半天后处理），总量在生成器能力范围内——但企业系统必须分期，因为跨库单据链有先后依赖。

### 三条落地原则

1. **一缩写一系统**：每个缩写独立建库，`erp_fin`、`crm_sales`、`mes_exec` 各自独立；单库超 100 张表即触发拆分评审
2. **底座先行，主链随后**：一期先统一组织树/账号/单据编码/审批底座——企业比校园更依赖组织树与多级审批流；治理层最后，没数据先建中台是空转
3. **已验证 SOP 全程复用**：每个系统走同一条 9 步流水线，已踩过的坑（枚举三件套、菜单同源、AI 推荐空、悬空外键）在模板层已修

## 二、三期路线图：每期都有"走通一条链"的验收口径

企业系统最怕的不是建不出来，而是建了一堆孤岛。所以每期验收不是"页面能开"，而是**跨库业务链走通**：

| 期 | 范围 | 周期 | 验收口径 |
|---|---|---|---|
| 一期·核心经营 | 5 系统，约 220 表 | 2~2.5 周 | **CRM 商机赢单 → 生成 ERP 销售订单 → 财务应收 → OA 归档**，跨四库一条单据链走通 |
| 二期·研产供物流 | 8 系统，约 230 表 | 2.5~3 周 | **PLM 变更 BOM → ERP 生产订单联动 → MES 派工 → QMS 检验 → WMS 完工入库**，制造主链走通 |
| 三期·支撑治理 | 5 系统，约 108 表 | 1.5~2 周 | **驾驶舱从指标库取数展示全链指标，GRC 控制矩阵勾稽到一期报销与采购单据** |

全案 20 系统约 30~35 人日，三期 6~9 周。单系统节奏按已落地系统实测推算约 1.5~2 人日。

## 三、UI 效果图先画给谁看

和智慧校园篇一样，20 张效果图先于代码产出，但用途完全工程化：

1. **立项汇报**：一张财务记账凭证页、一张 MES 工序看板，比 60 页 PPT 更能说服业务部门——他们一眼知道自己未来的工作界面长什么样
2. **开发 UI 契约**：效果图的布局 = 生成器模板布局；页面上的每个统计卡片、每个筛选条件、每个操作按钮 = 后端的接口清单。**效果图的信息结构就是接口需求文档**，评审效果图等于评审 API 设计

每张效果图标注：系统名、库名、表规模、页面路由（如 `erp-fin.hcgroup.com:8150/voucher/PZ2026030158`）——路由里的单据号就是单据链追溯的锚点。

### 三张代表页，看效果图怎么"说话"

**① ERP·财务·记账凭证**——页首三个统计卡直击财务痛点：

- 本月凭证 1,284 张（↑12%）
- 借方合计 ¥86,420,350.00 = 贷方合计 ¥86,420,350.00，**借贷平衡**徽标亮起
- 23 张未过账凭证"需今日处理"

凭证分录表里"销售华为技术货款"一笔拆成三行：1122 应收账款借方 226 万 / 6001 主营业务收入贷方 200 万 / 222101 销项税贷方 26 万——合计行自动校验平衡。这个页面的信息结构直接翻译成后端接口：`凭证分录列表`、`借贷合计校验`、`待过账计数`。

**② TMS·调度配载**——一屏讲清"整车零担混装"：

- 配载方案 DD20260322-01（沪G 挂车 40 吨厢式）装 3 张运单：武汉中车株洲 8.6 吨第 2 卸、武汉美的 11.2 吨第 1 卸、长沙格力 6.8 吨第 3 卸
- 装载率 26.6/40 吨 = **66.5%**，运费 ¥8,240（里程+吨位+卸货点）
- 在途跟踪节点条：工厂装车 → G4201 转运 → 武汉绕城 → 中车株洲 → 签收回单，GPS 显示"武汉绕城高速 K42 · 时速 82km/h"，同挂车的美的单已延误 40 分钟标黄

**③ BI·集团经营驾驶舱**——设计稿上就写死了纪律：

- 本月销售收入 ¥1.28 亿（达成 91%）、毛利率 31.2%、应收 ¥4,860 万、存货周转 46 天（目标 ≤50）
- 每个指标角标注明来源指标编码——**BI 只做展示，口径永远只有一份（从指标库取数）**，这是三期最容易返工的地方

## 五、跨系统五大决策：企业版比校园版多两件大事

登录、待办、跨库外键、编码规则、种子数据这五件套校园篇讲过，企业场景里有两条要加重：

1. **主数据归属（一物一主）**：物料主数据归 `erp_scm`、客户归 `crm_sales`、供应商归 `scm_srm`、BOM 归 `plm_life`——其余系统只存编码引用。企业系统 80% 的数据不一致事故都源于主数据多头维护
2. **计算引擎边界（生成器不做伪计算）**：APS 排程算法、薪酬算薪引擎、SCADA 采集协议（OPC UA/Modbus）、BI 取数 SQL 全部外置为适配器——生成器只管"模型 + 台账 + 流程"，产物里只出现台账与流程表。硬在生成的 CRUD 里做排程算法，交付的一定是"假智能"
3. **跨库单据链不建外键**：跨系统引用存"系统标识 + 业务单号"（如 ERP 销售订单里存 CRM 商机号），追溯链路由 OMS/BI 聚合展示——跨库外键是分布式数据一致性的天坑
4. **单据编码一期锁定**：`单据前缀 + 年月 + 流水`（如 SO-202603-0001），避免各系统自治后无法对账
5. **组织与账号真源**：一期 erp_oa/底座统一组织树与账号，其余系统共享登录态接入

## 六、单系统 9 步 SOP（与智慧校园同源，全部复用）

```
S1 功能设计     —— 缩写拆子域（ERP 先拆 3 子域再建 3 库）
S2 tables JSON  —— 业务表字段内嵌 + 15 张通用表
S3 校验         —— --check-labels 校验关联配置
S4 流水线       —— ddl-preview → create → prepare-db → 12 步（60 表 ≈ 7 分钟）
S5 菜单重规划   —— 按子域三级结构重写路由与菜单（路由菜单同源）
S6 页面级后处理 —— polish_enums_refs + 悬空外键清理（企业单据行表外键密度高，必跑）
S7 演示数据     —— 真实业务口径灌库（一条订单从 CRM 流到 OMS 的主线，不做假乱数）
S8 三层验收     —— 前端 build ✓ + 后端 compile ✓ + 逐页截图 console 0 错误
S9 沉淀         —— 坑库查漏补缺 + CSDN 实战文一篇
```

## 七、企业场景特有的四个坑（全部来自已踩坑记录）

1. **巨型单体诱惑**：ERP/CRM 是"一个词"，但绝不是一个库——任何单库超 100 张表即触发拆分评审
2. **业务枚举错配通用映射**：企业系统枚举密度远高于校园（单据状态/审批状态/检验结论/库位类型/装载类型…），页面级后处理必须 grep 复查非 status 字段误指通用 `enumText('status')`
3. **悬空外键井喷**：人才培养方案系统实测 861 条悬空引用全靠 `--fix-dangling` 清理；企业系统的 BOM/工艺路线/单据行外键只多不少，S6 必跑且验收时 grep 复查
4. **计算类需求越界**：排程/算薪/取数一律适配器外置。接受"生成器不做计算"这条边界，APS/薪酬/BI 才不会烂尾

## 九、下一步：先拿 CRM 打样

20 个系统里 **CRM 是最佳打样对象**：30 张表、线索/商机/报价/合同四域清晰、和已落地的费控审批底座天然衔接。跑通 CRM 后并行铺 ERP 三库，一期其余系统批量复制。

另一个值得做的模板增强：`vuePage.ftl` 增加**单据主子表**模板区块——ERP/MES/WMS 的单据头-行结构占比约 40%，比逐页手改效率高一个量级。
