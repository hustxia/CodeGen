**问题**：生成的系统对「收钱」这件事是空白。业务表里常见的需求（培训缴费、订单收款、押金）都要用户手工对接 SDK、处理验签幂等、考虑回调安全——这是生成器覆盖面上最后一块「人人都要、人人重写」的能力。

## 二、主题与理由

**主题：产物「支付能力包」——系统级开关 `pay_enabled` 生成通用支付模块：`pay_order` 支付单表 + `PaymentService` 渠道抽象（wechatpay-native / alipay-page / mock 三实现）+ 收银台前端；业务表按约定字段接入，回调验签幂等内置。**

理由：

1. **渠道抽象是本版的核心资产**：业务代码只面对 `PaymentService`（下单/查单/关单/退款），渠道实现可插拔——用户拿到商户资质前用 mock 跑通全流程，拿到后改 yml 即切真渠道，零代码改动；
2. **mock 渠道解决「无资质/无公网」死锁**：流水线自检和本地联调都不依赖真实商户号与公网回调，产物开箱即可演示完整支付流（与 V5.0「开箱即跑」原则一致）；
3. SDK 风险已清零（中央仓库直供），边际成本全在模板与抽象设计——正是生成器最擅长的部分。

## 三、范围

### P0-1 支付模块模板（产物侧）

- `sys_project.pay_enabled`（tinyint，缺省 0）——开启时 scaffold 生成支付模块：
  - 表模板：`pay_order`（id/out_trade_no 唯一键/subject/amount 分单位/pay_channel/pay_status 0待支付 1成功 2关闭 3退款/business_type/business_id/回调原始报文/审计列）——进 `db.sql`，自检标准列同步
  - 依赖：`wechatpay-java` + `alipay-sdk-java`（版本进产物 BOM 统一管理）
  - `common/pay/PaymentService` 接口 + 三实现：`WxPayNativeService`（扫码）、`AliPayPageService`（电脑网站）、`MockPayService`（本地假支付：直接置成功并触发与真渠道同构的状态流转链路）
  - 渠道由 yml `pay.channel=mock|wxpay|alipay` 选择，缺省 **mock**（保证无资质也能跑）
- 密钥全部 `${PAY_MCH_ID:}` 式环境变量占位符，主 yml 零明文（**硬依赖 V6.2 P0-3 的占位符机制，若 V6.2 未落地则本版内联实现同一套**）

### P0-2 下单 / 回调 / 查单端点（产物侧）

- `POST /pay/order`（业务侧创建支付单→渠道下单→返回二维码/跳转 URL）、`POST /pay/notify/{channel}`（异步回调：**验签 → 幂等落库（out_trade_no 唯一约束兜底）→ 状态机流转 → 返回渠道要求的应答格式**）、`GET /pay/order/{outTradeNo}`（主动查单，**回调不可达时的补偿手段**）、`POST /pay/close/{outTradeNo}`
- 回调安全三件套内置在模板里：微信 V3 证书验签（`NotificationParser`）、支付宝 RSA2 验签、金额二次校验（回调金额必须等于支付单金额，防篡改）
- **回调不可达兜底**：定时查单补偿任务（@Scheduled 可配开关）——本机/内网部署不配公网也能靠轮询对账把状态收对，回调只是加速器不是唯一通路

### P0-3 前端收银台（产物侧）

- 收银台页：渠道选择（mock 显示「模拟支付」按钮）→ 扫码弹窗（zxing 生成二维码，前端生成零后端依赖）→ 支付结果轮询（查单接口 2s 间隔，成功跳转）
- 「支付记录」管理页：pay_order 列表 + 状态徽标 + 手动关单/查单按钮（复用 vuePage 模板样式体系）
- 业务表接入约定：业务表含 `pay_status` 字段时，页面详情自动显示「去支付」入口（模板条件块，无侵入）

### P0-4 流水线与自检接线

- 自检新增：支付模块存在性、mock 渠道下单→成功→查单全链路断言（产物 health 步后可跑）
- 人事系统验收样板：`employee_profile` 押金场景或新建 `demo_fee` 缴费表，mock 渠道端到端走通

### P1（本版尽力，不做门禁）

- 微信 JSAPI/H5 支付（公众号/手机浏览器场景）、支付宝手机网站支付
- 退款端点（`/pay/refund`，两渠道 SDK 均支持，状态机加 3 已退款流转）
- 业务表级绑定 `pay_code`（仿 V2.2 `flow_code` 模式：一张业务表挂一个支付场景配置）
- 支付宝沙箱 profile 预置（`pay.profile=sandbox`）

### P2（明确不做，下版再说）

- **平台代收付/资金归集**——合规红线（二清），平台永远只生成代码不碰钱
- 小程序支付（依赖小程序侧改造，超出产物 Web 边界）
- 聚合支付服务商/服务商分账模式
- 对账单文件下载与自动对账（真实商户场景再上）

## 四、关键设计决策

| 决策点 | 定案 | 理由 |
|---|---|---|
| 集成粒度 | M1 系统级能力包（pay_order 通用支付单），不做表级绑定 | 支付单与业务单解耦（business_type/business_id 关联）是标准做法；表级 `pay_code` 绑定留 P1，避免一步到位设计过重 |
| 渠道切换 | yml 单选 `pay.channel`，缺省 mock | 无商户资质/无公网也能全流程演示；真渠道接入=改配置不改代码；mock 与真渠道走同一条状态流转链路，测试等价 |
| 回调可靠性 | 验签+幂等+金额二次校验+**主动查单补偿**四层 | 回调在本地/内网必然不可达，查单补偿必须是一等公民而非可选优化；这也是支付对接最常见的翻车点 |
| 金额规范 | 数据库**分**（bigint）存储，展示层转换 | decimal 浮点误差是支付资损经典坑；pay_order 与业务表金额字段统一分存储 |
| 密钥管理 | 环境变量占位符，主 yml 零明文 | 商户私钥泄露=资金风险；复用 V6.2 P0-3 机制，保持产物配置安全标准统一 |
| 微信无沙箱 | M1 靠 mock 覆盖联调，真渠道验收用 0.01 元真实交易 | 事实如此，不硬造沙箱；文档如实写明 |

## 五、验收标准

1. 新建系统勾选 `pay_enabled` → 流水线跑通 → 产物含 pay_order 表、支付模块、收银台页，自检 mock 全链路（下单→成功→查单）通过
2. mock 渠道：业务表（含 pay_status）详情页「去支付」→ 收银台 → 模拟支付 → 业务表 pay_status 联动更新，pay_order 全程留痕
3. 配置真实商户凭据 + `pay.channel=alipay` → 支付宝沙箱（P1 预置后）全流程通过；微信渠道 0.01 元真实交易回调验签、幂等重放（连发两次同 out_trade_no 回调）均正确
4. 断网/无公网环境：主动查单补偿任务把 30 分钟前 mock 单据状态收对
5. 产物 yml 全文无任何明文密钥（占位符 + local.yml.example 引导）
