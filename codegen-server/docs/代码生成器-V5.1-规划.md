# 代码生成器 V5.1 规划 —— 一句话建系统完善：DDL 审计列自动补齐

> 日期：2026-10-24　状态：规划待过目
> 前置：无（V5.5 多模块收尾与本版无代码耦合，可并行）

## 一、现状核对（2026-10-24 实测）

| 项 | 现状 | 位置 |
|---|---|---|
| 审计列标准 | `id, create_time, update_time, create_by, update_by, deleted` | `GenPipelineServiceImpl:58 AUDIT_COLS` |
| AI 模式 | **已自动补齐**：`buildDdl` 统一插 id 主键 + 5 审计列，用户无感 | `GenPipelineServiceImpl:218` |
| 手动 DDL 模式 | **阻断**：`lintDdlText` 发现缺列即拒绝，报「补齐后重试，或改用 AI 模式」——用户得自己改 SQL | `GenPipelineServiceImpl:165-172` |
| 已建表检查 | `lint(dbName)` 报缺失列并**生成** `fixSql`（ALTER 语句），但只提示不执行 | `GenPipelineServiceImpl:352, 391 fixColumns` |

**问题**：同一个「审计列齐全」目标，AI 模式自动、手动模式靠人。用户粘贴存量 DDL（最常见的恰恰是没有审计列的老库导出）直接被挡；已建表缺列也要复制 ALTER 手工执行——流水线「全程不碰数据库」的承诺在手动路径上没兑现。

## 二、主题与理由

**主题：审计列「有则跳过、没有自动补齐」——手动 DDL 与已建表两条路径全部自动化，补齐明细如实报告。**

理由：

1. `fixColumns` 已经是完整的 ALTER 生成器（单一实现），差的只是「执行它」这一步——改动小、收益直接。
2. 与 V5.0 目标一致（全程不碰库、不看日志排错）；缺列阻断是 V5.0 M1 的临时保守，现在补上自动化。
3. 补列是**纯增量**操作（ADD COLUMN，不动用户已有列），风险在六类 DDL 操作里最低，适合默认自动化。

## 三、范围

### P0-1 手动 DDL 录入自动补齐（改写后执行）

`prepareDb` manual 分支：`lintDdlText` 发现缺列不再阻断，改为**改写 DDL 文本**后执行：

- 改写规则（只增不改）：在 CREATE TABLE 列定义段末尾插入缺失的审计列（与 AI 模式 `buildDdl` **同一定义**——单一实现抽出 `auditColumnDefs()` 供两处共用）；无 `id` 列时补 `id bigint AUTO_INCREMENT + PRIMARY KEY`
- 用户已有列/类型/注释/业务列一概不动；已含某审计列的表跳过不动
- 响应新增 `auditReport`：每张表 `SKIPPED`（六列全齐）/ `PATCHED`（补了哪几列），前端录入结果区展示明细徽标

验收：粘贴无审计列的老库 DDL → 建表成功 → information_schema 实查六列齐全，且业务列与原文一致。

### P0-2 已建表自动补齐（执行 ALTER）

`lint(dbName)` 升级为可执行：新接口 `POST /gen/pipeline/{id}/lint/fix`——对报告里 `missingCols` 非空的表，逐表执行 `fixColumns` 现成 ALTER 语句，执行后复检：

- 幂等：执行前逐列查 information_schema（MySQL 8 不支持 `ADD COLUMN IF NOT EXISTS`），已存在即跳过——防并发双击重复加列
- 报告每表执行结果：`PATCHED`（补了哪些列）/ `SKIPPED`（已齐）；失败表列出原因并继续其余表（一表失败不拖垮整批）
- 原 `lint` 接口保持只读 dry-run 语义不变

验收：手工建一张只有 `id` 的表 → lint 报 5 列缺失 → fix → 复检 ok=true，产物生成不再被 lint 挡。

### P0-3 前端接线

- 录入弹窗（手动 DDL）：提交后结果区展示 `auditReport` 徽标（补齐表数 + 缺列明细），替代现在的报错弹窗
- 流水线详情 lint 步骤：加「一键补齐」按钮（调 fix），执行后自动刷新 lint 状态；按钮在 ok=true 时禁用

### P1（本版尽力）

- 审计列清单常量上 yml（`gen.pipeline.audit-columns`），特殊系统可增删
- 产物头注释写生成器版本号（为将来逆向/漂移检测预埋，V6.0 规划已提及）

### 明确不做

- 不纠正「已存在但类型不符」的审计列（如用户的 `create_time` 是 varchar）——只补缺，不改错，报告里提示类型差异
- 不回填存量行的 create_by 等业务数据
- 不改动 AI 模式行为（已达标）
- DDL 中 `DROP TABLE`/`ALTER` 混合语句的改写（只处理 CREATE TABLE）

## 七、风险

1. **DDL 文本改写**：CREATE TABLE 书写风格千差万别（列定义跨行/行内注释/反引号缺失）——改写器只依赖 lintDdlText 已验证的解析边界，解析不了的表**降级为阻断**（维持现状报错），绝不模糊匹配改错 SQL。
2. **补主键对非空表**：MySQL 支持在线加自增主键（自动回填），但超大表有锁表时长——流水线场景是新库小表，风险可忽略；报告里如实标注。
3. **与 AI 模式漂移**：补列定义两处共用一个函数后，AI/手动产物完全一致，不存在分叉（契约测试守护）。
