# 代码生成器 · 定时建模提速方案（ElasticJob 评估）

> 状态：待决策（本文档只做方案，不含代码）  
> 起草：2026-10-25  
> 背景：夜间定时任务（scripts/nightly-fullgen.mjs + Windows 计划任务）跑"完整系统"模式时，本地 Ollama（qwen3-8b-8k，纯 CPU）生成 50-100 张表需 1-2 小时，用户觉得太慢，提出想用 ElasticJob 调用大模型。

---

## 一、先对齐问题：慢的根因不是调度器

| 环节                          | 耗时           | 换 ElasticJob 有没有用 |
| --------------------------- | ------------ | ----------------- |
| 模型推理（Ollama CPU，~2.5 tok/s） | **占总耗时 99%** | ❌ 完全无关            |
| HTTP 调度/脚本逻辑                | 秒级           | ❌ 无关              |
|                             |              |                   |
| 建库建表执行                      | 秒级           | ❌ 无关              |

结论：**单机 + 本地 CPU 模型场景下，引入 ElasticJob 提速收益 ≈ 0**。它的真实价值在"多机分片并行"和"企业级调度管理"。是否引入取决于你要哪一个。

---

## 二、真正能提速的路（按收益排序）

| 路线                                       | 提速倍数         | 成本                 | 说明                                                                             |
| ---------------------------------------- | ------------ | ------------------ | ------------------------------------------------------------------------------ |
| **A. 换云端大模型 API**（DeepSeek/Qwen-Max/智谱等） | **20-100 倍** | 按量付费，100 张表约几毛-2 元 | 改 `application-local.yml` 的 base-url/model 即可，代码零改动（OpenAI 兼容协议已通）；白天+夜间都能秒级响应 |
| B. 云 GPU 跑 Ollama（租 4090/A10）            | 10-30 倍      | 约 2-3 元/小时         | 保留本地架构，把 Ollama 搬上云，脚本 base-url 指向云主机                                          |
| C. Ollama 并发（单机跑 2 个并行请求）                | 1.3-1.8 倍    | 零成本，但 15.8GB 内存吃紧  | OLLAMA_NUM_PARALLEL=2；CPU 核数会被摊薄，收益有限                                          |
| D. Token 减量（提示词精简、每模块 3→4 表、禁用长尾字段）      | 1.2-1.4 倍    | 零成本                | 已基本做过（8K ctx / no_think），剩余空间小                                                 |
| E. 换更小模型（qwen2.5-coder:3b）               | 2-3 倍        | 质量明显下降             | 3 张表测试期可用，100 张表质量扛不住                                                          |

**推荐组合**：A（换云端 API，改两行配置）为主；夜间跑时零成本、白天用云端快速迭代，本地模型保留做离线兜底。

---

## 三、ElasticJob 方案（如果你确实要引入）

### 3.1 适用前提（满足其一才有价值）

1. **多机/多推理节点**：≥2 台机器各跑一份 Ollama（或云端 GPU 节点），分片才有并行收益
2. **调度统一收敛**：不再用"Windows 计划任务 + 独立脚本"，任务管理、重试、分片、可视控制台都收进 codegen-server（Java 技术栈内闭环）

两者都不满足时，建议用 **Spring @Scheduled + 数据库任务表** 替代 ElasticJob——零外部依赖就能拿到重试/台账/手工触发，不需要 Zookeeper。

### 3.2 技术选型

| 项    | 选择                                            | 理由                                                              |
| ---- | --------------------------------------------- | --------------------------------------------------------------- |
| 框架   | ElasticJob-Lite 3.x（内嵌模式，Spring Boot starter） | 不需要独立调度中心进程                                                     |
| 注册中心 | Zookeeper 3.8（本机单节点）或 etcd                    | 必选外部依赖；**注意 15.8GB 内存机器上要多养一个 ZK 进程（约 500MB-1GB），且需加入 360 白名单** |
| 作业类型 | 分片作业（SimpleJob + ShardingStrategy）            | 按业务模块分片                                                         |

### 3.3 作业设计

```
作业1：夜间建模总调度（每天 02:00 触发）
  ├─ 读 nightly-jobs.json / 数据库任务表（enabled 开关语义不变）
  ├─ 对每个系统：调 ai-modules 拆出 N 个业务模块
  └─ 以「系统 × 模块」为分片项，总数 = Σ模块数

作业2：模块建表分片作业（分片并行执行）
  ├─ 分片参数 = pipelineId + moduleName
  ├─ 每分片：POST /gen/pipeline/ai-model（该模块建表）
  ├─ 断点续跑：以 (pipelineId, moduleName) 去重，已成功的分片直接跳过
  └─ 失败重试 3 次 + 失效转移（某节点挂了分片自动漂到别的节点）

作业3：汇总建库作业（依赖作业2全部分片完成）
  └─ 合并各模块表结构 → createPipeline → prepare-db → seed(V5.2) → 停在建表
```

### 3.4 并行收益的真实账

| 部署形态                | 分片并行收益                                  |
| ------------------- | --------------------------------------- |
| 仅本机 1 个 Ollama（现状）  | ≈ 0（CPU 就那么多，2 个并行请求互相抢核，总吞吐最多 +30-50%） |
| 本机 + 1 台云 GPU 节点    | ≈ 2 倍                                   |
| 3 个推理节点（1 本地 + 2 云） | ≈ 3 倍，100 张表 100 分钟 → 约 35 分钟           |

### 3.5 与现状的衔接/风险

- **夜跑脚本退役**：ElasticJob 上线后 `nightly-fullgen.mjs` 与 Windows 计划任务下线，`nightly-jobs.json` 的 enabled 开关语义迁到任务表，**两套调度不能并存**（会重复跑）
- **内存红线**：ZK（约 1GB）+ codegen-server（约 1GB）+ Ollama（8B 模型约 5-6GB），15.8GB 机器接近上限，再跑前端 dev server 需盯内存
- **360 拦截**：ZK 的 java 进程、快照目录必须加白名单（踩过 qhjwsp-agent 删文件的坑）
- **学习/运维成本**：分片参数设计、控制台部署、ZK 故障排查，都是长期维护面

## 四、决策建议

| 你的真实诉求                          | 建议                                                                                   |
| ------------------------------- | ------------------------------------------------------------------------------------ |
| **就是嫌 100 张表跑得慢**               | ❌ 不上 ElasticJob。✅ 把 `application-local.yml` 切到云端 API（方案 A），几行配置，提速 20-100 倍，本地模型留作兜底 |
| 想把定时任务收进平台统一管理（页面看进度/重试/启停）     | 用 **Spring @Scheduled + 任务表**（轻量，无新依赖），不值得为单机引 ZK                                    |
| 未来确定要**多机并行**跑建模（本地+云 GPU 混合集群） | ✅ ElasticJob 才划算，按 3.2-3.4 落地，预计排 V5.4                                               |

**我的推荐**：第一步先切云端 API 验证速度（改动最小、立竿见影）；如果你确实要 ElasticJob，走"多机并行"前提，作为 V5.4 立项。
