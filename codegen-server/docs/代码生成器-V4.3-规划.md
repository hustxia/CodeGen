# 代码生成器 V4.3 规划：模板回归与质量护栏

> 编制时间：2026-10-22 17:10
> 前置版本：V4.2「生成结果可信化」已落地并推送（后端 `9dfa8be`、前端 `49a7e7a`，dev 分支）
> 本版主题：**让"改模板 / 改策略"从"手点一遍看运气"变成"跑一条命令看结论"**

---

## 一、现状核对（全部为 17:00 实测，非推测）

### 1.1 功能侧：不缺功能

| 维度 | 实测 | 判定 |
|---|---|---|
| 生成模板 | 12 个 FTL，2,338 行；单页面产物 1,142 行，单 Controller 669 行 | 覆盖 CRUD / 导出 / 导入 / 导入模板 / 主子表 / 三级明细 / 流程 / 字典 / 唯一性校验 / 按钮权限 |
| 模板可编辑 | `gen_template` 12 条在线可改，带版本历史、回滚、FreeMarker 语法校验 | 能力齐 |
| 生成链路 | `/gen/parseDdl` `/gen/db/import` `/gen/diff` `/gen/write` `/gen/verify` `/gen/self-check` `/gen/scaffold` `/gen/db/execute-ddl` | 从建表到起服务闭环 |
| 可信化（V4.2） | 台账合一、漂移检测、回滚预览、台账巡检 | 已上线 |

结论：**不必再加功能点**，再堆功能只会把未验证的面积继续扩大。

### 1.2 质量侧：护栏近乎为零

| 维度 | 实测 | 判定 |
|---|---|---|
| 后端测试 | 197 个主类 vs **7 个测试类 / 54 个用例**（类覆盖 3.6%），且全部是纯函数（路径回落、命名一致性、开关默认值、漂移判定、回滚判定、模板渲染） | **Controller / Service / 写盘链路零接口测试** |
| 前端测试 | 22 个 Vue、6,997 行，**0 个测试文件**，`package.json` 里没有任何 test 依赖 | 零护栏 |
| Lint | `npm run lint` 实际报 `command "lint" does not exist`（缺 eslint 插件） | 假命令，早已失效 |
| CI | 无 `.github/workflows`、无 `.gitee`、无 Jenkinsfile | `mvn test` 靠人记得跑 |
| 产物基线 | 无 `baseline` / `golden` 目录 | **模板一改，产物变没变只有人眼能发现** |
| 模板版本历史 | `gen_template_history` 表 **0 行**（能力在，从未用过） | 改模板没有任何历史对照 |
| 复杂度 | `GenScaffoldServiceImpl` **1,953 行**，占 impl 9,538 行的 20.5% | 最危险的功能（扫描/写盘/编译/起服务）也是最难测的一块 |

### 1.3 结论

V4.2 解决的是"**写没写对**"（台账、漂移、回滚都能自证）。
下一层缺的是"**生成出来的东西对不对**"——模板是产品的真正内核（2,338 行模板产出几千行代码，辐射到每个被接管的工程），但改模板这件事目前**没有任何回归锚点**：

- 改错一个 `<#if>`，产物语法错误 → 只有跑到目标工程编译失败才发现；
- 改对但改变了缩进/顺序 → 没人知道，也没有 diff 可看；
- 想改回来 → `gen_template_history` 是空的，只能凭记忆。

**这是当前最大的风险敞口，也是本版要解决的问题。**

## 二、主题与目标

**主题：模板回归与质量护栏。**

目标三条，可度量：

1. 改一个模板字符，能在 **30 秒内**知道"影响了哪些文件的哪几行"；
2. 写盘 / 漂移 / 回滚三条链路的不变式，**每次提交自动验证**，不靠手点；
3. 一条命令给出全绿结论，任何人（含 CI）都能执行。

---

## 三、任务清单

### P0-1 产物黄金基线（规模 M）

**做什么**
- 在 `src/test/resources/gen-baseline/` 下固定三个样板用例：
  - `simple`：单表 + 字典字段（覆盖 dictText、下拉、标签渲染）
  - `relation`：外键 + 多选回显（覆盖 `/bind-values`、`/options`）
  - `master-detail`：主子表 + 三级明细（覆盖 `save-with-children`、`with-children`）
- 测试用内存构造的 `GenTable` + 列配置渲染全部 12 个模板，与基线逐字节比对；
- 不一致时输出 **unified diff**，明确"文件 + 行号 + 差异内容"，而不是一句 assert failed。

**关键设计**
- 基线更新必须显式开关：`mvn test -Dgen.baseline.update=true`；默认只读。
  否则「跑挂了就更新基线」会把真实回归永久抹掉——这是基线机制最常见的死法。
- 基线文件本身进 git，模板变更与基线变更必须在同一个提交里出现，评审时一眼可见。

**为什么不做成"生成后编译通过"**
编译只能证明语法对，证明不了"该有的块还在"。有基线后编译可作为第二道，本版先立基线。

### P0-2 接口契约测试（规模 M）

**做什么**
- `@SpringBootTest` + MockMvc，写盘目录用 `@TempDir` 沙箱，**绝不碰演示工程**；
- 覆盖 6 条关键链路：`/gen/diff`、`/gen/write`、`/gen/drift`、`/gen/history/rollback/preview`、`/gen/history/rollback`、`/gen/ledger/health`；
- 固化四条不变式（这就是 V4.2 承诺过、但目前只有人工脚本验证过的部分）：

| 不变式 | 断言 |
|---|---|
| 台账完整 | 写盘后 `gen_output` 新增行数 == 磁盘实际变更文件数 |
| 备份可信 | `OVERWRITTEN` 行的 `prev_md5` == 备份文件 md5 |
| 回滚可逆 | 回滚后文件 md5 == 覆盖前 md5（首次生成则文件不存在） |
| 回滚可再回滚 | `RBK` 批次自身可回滚，回滚后回到回滚前状态 |

**数据库策略**
优先评估 H2 兼容性（现有 SQL 用了 `SUM(status='ERROR')` 这类 MySQL 方言，大概率不兼容），不兼容则建独立 schema `gen_platform_test`，测试启动时建表、结束清库；**不连开发库**。

### P0-3 前端策略层抽取 + 单测（规模 S）

**做什么**
- 把散在 `views/gen/wizard/index.vue`（648 行）与 `views/gen/output/index.vue` 里的推导逻辑抽到 `src/utils/genStrategy.js` 纯函数：
  - `resolveWriteFlags(strategyMode)` → `{ overwrite, skipDrifted }`
  - `countSkipped(rows, strategyMode)`
  - `rollbackDefaultSelection(items)` → 默认勾选规则（会动文件且未手改）
- vitest 覆盖，目标 12~15 例；
- 顺手修掉 `npm run lint` 假命令（补 eslint 配置或用 `eslint` 直调）。

**抽取顺序（重要）**
先写「现状快照测试」——拿当前实现跑 20 组输入把输出固化下来，再搬代码，搬完快照必须全绿。否则"重构"会变成"改需求"。

### P0-4 一条命令全绿（规模 S）

**做什么**
- `scripts/verify-all.mjs`：`mvn test` → `vitest run` → `npm run build:prod`，任一失败即非 0 退出；
- 前端 `build:prod` 目前只在本机正常环境跑得通（当前沙箱会拦 dist 删除），脚本里要如实报出环境原因而非静默跳过；
- 提交 Gitee Go 流水线配置，`push dev` 自动跑。

### P1-1 拆 GenScaffoldServiceImpl（规模 L）

1,953 行按现有职责拆成 4 个协作者，**只搬不改**：

| 协作者 | 职责 |
|---|---|
| `ProjectScanner` | 探测目标工程结构、包名、模块 |
| `ArtifactWriter` | 生成物落盘（复用 V4.2 台账） |
| `BuildRunner` | mvn/npm 构建 |
| `ServiceLauncher` | 启动目标服务并探活 |

分 4 次小提交，每次跑 P0-2 契约测试兜底。本项排在 P0 之后，因为**没有测试网的拆分是赌博**。

### P1-2 模板影响面预览（规模 M）

改模板前选表 → 显示"将影响哪些表的哪些文件"（复用 diff 的 `fileGroup`/`side` 事实 + 模板 key → 产物映射）。解决"改一个公共模板，不知道动了多少工程"的恐惧。

### P2 收尾

- 6 条孤儿台账记录（`GEN20261021113435`，demo_category/goods/order）——确认后清理；
- 前端生产包重新打包并归档。

## 四、验收标准

| 项 | 标准 |
|---|---|
| 测试规模 | `mvn test` ≥ 90 用例（现有 54 + 基线 ≈12 + 契约 ≈15 + 其余），全绿 |
| 基线有效性 | 手动删掉模板里一个 `<#if>`，基线测试必须红，且 diff 指到具体行 |
| 基线安全性 | 不传 `-Dgen.baseline.update=true` 时，测试只读不写 |
| 不变式常驻 | 四条不变式在 CI 日志里逐条可见，不依赖本地脚本 |
| 一条命令 | `node scripts/verify-all.mjs` 在任何一台干净机器上给出结论 |

## 五、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 基线僵化，正常演进被红拦住 | 团队开始"先更新基线再看" | 更新必须显式开关；PR/提交说明里贴基线 diff 摘要，让变更可视化 |
| 契约测试连开发库 | 测试污染真实台账 | 独立 schema，`@TempDir` 沙箱；测试启动前断言库名带 `_test` |
| 前端抽取变成改行为 | 隐性回归 | 先固化现状快照，再搬代码；快照与实现同时提交 |
| 拆脚手架类引入回归 | 最危险功能被改坏 | 纯搬迁、分步提交、契约测试兜底；本版允许其继续"大"，但不允许"边拆边优化" |
| H2 兼容性差导致工期膨胀 | P0-2 卡住 | 先做 30 分钟兼容性验证（跑一遍现有 DDL + 两条典型 SQL），不通就改独立 MySQL schema，不硬啃 H2 |

## 六、备选主题与代价（若不想走质量线）

| 备选 | 内容 | 代价 |
|---|---|---|
| B1 CLI 生成 | `codegen-cli` 脱离 UI 生成 | 模板无基线时，CLI 只会把错误更快地放大到流水线 |
| B2 生成即启动 | 生成 → 编译 → 起服务 → 冒烟一条龙 | 已有雏形（scaffold + self-check），缺的正是"可重复的断言"，本质仍是本版 |
| B3 逆向接管存量工程 | 从已有代码反推表配置 | 工作量最大，且接管越多，模板回归风险越大——顺序反了 |
| B4 多应用 / 多租户 | 一套平台托管多个业务系统 | `sys_project` 目前仅 1 条，需求未被验证 |

**推荐 A（本版主题）**：B1/B2/B3 都依赖"模板改动可验证"这个前提，先立地基。

## 七、本版明确不做

- CLI / 逆向 / 多租户（依赖本版结论）
- 权限体系重构（当前按钮级权限已够用）
- 主题继续扩展（240 套已覆盖到过设计冗余）
- 生成能力新增（导入导出、主子表、流程都已具备）

## 八、执行顺序建议

```
P0-3（前端抽取，最轻，先建立"改代码有测试"的体感）
  ↓
P0-1（产物基线，价值最高）
  ↓
P0-2（接口契约，兜住写盘链路）
  ↓
P0-4（一条命令 + CI，把上面三项固化）
  ↓
P1-1（拆脚手架） / P1-2（影响面预览）
```

先做 P0-3 的理由：它最小、见效最快，且抽出来的纯函数会成为 P0-1/P0-2 断言里复用的判定逻辑。
