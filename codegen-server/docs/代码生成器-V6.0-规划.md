| 项 | 现状 | 位置 |

**问题**：V5.5 交付的是「微服务就绪单体」——模块边界画好了，但跨模块仍是进程内直调、单库单配置。要真正拆服务，还缺：注册中心、统一入口（网关）、跨服务调用契约、配置中心。

## 二、主题与理由

**主题：`project_structure='micro'` 第三态——在多模块结构上生成 Nacos + Gateway + OpenFeign 设施，一个系统可从「单体运行」平滑切到「多服务运行」。**

为什么是现在：

1. 用户原始诉求（2026-10-24「支持微服务，代码生成支持多个模块」）的下半场——多模块已交付，微服务设施是既定钩子（V5.5 需求文档明文「留下一版」）。
2. 逆向工程方案被否（2026-10-25），版本空位需要新主题；备选里微服务设施价值最直接。
3. 本机已有 Nacos 环境（shop 项目），验收可实测注册与路由，不是纸面交付。

## 三、范围

### P0-1 第三态 'micro'：结构升级

- `sys_project.project_structure` 增值 'micro'：在 multi 四模块基础上**加生成 `<stem>-gateway` 模块**（五模块）
- 依赖升级（micro 专属）：spring-cloud 2023.0.x BOM + `spring-cloud-starter-alibaba-nacos-discovery/config` + `spring-cloud-starter-gateway` + `openfeign`
- **开关式降级**：`nacos.enabled=false`（默认）时 micro 产物与 multi 行为一致——服务仍可独立 `mvn spring-boot:run`，保证「没装 Nacos 也能跑通生成物」；为 true 时启动即注册
- bootstrap 模块加 `bootstrap.yml` 模板（Nacos config import，enabled=false 时注释态）

### P0-2 Gateway 模块生成

- `<stem>-gateway`：Spring Cloud Gateway（webflux），按系统内业务模块聚合路由：`/{moduleName}/**` → `lb://<stem>-bootstrap`
- 网关端口独立（`<serverPort+1>`，可配）；跨域/鉴权透传模板（AuthContextFilter 的 token 头在网关层透传不解析）
- 单体模式（nacos.enabled=false）路由降级直连 `localhost:serverPort`——网关存在但不依赖注册中心

### P0-3 OpenFeign 跨模块调用

- 生成期边界：主从表 with-children 校验主从表必须**同模块归属**（同在 service 模块，现状天然满足；跨系统引用生成期报错拦截）
- service 模块生成 Feign 客户端模板骨架（`<stem>-service` 内 `remote/` 包）：示例接口 + `@FeignClient(name = "<stem>-bootstrap")`，nacos.enabled=false 时用 url 直连兜底
- M1 不做「按表配置自动生成跨服务 API」——只给骨架与约定，跨服务接口按需手写（诚实边界：自动推导跨服务契约复杂度高，等真实场景）

### P0-4 前端适配

- apiJs 模板 baseURL 逻辑：micro 且网关启用 → `/{modulePath}`（走网关路由前缀）；其余维持现状
- 前端工程不拆（V5.5 边界延续）

### P1（本版尽力，不做门禁）

- 产物头注释写入生成器版本号（`@generated V6.0`）——多服务场景排障时能认产物出自哪版生成器
- 自检标准列告警 + 非 id 主键支持（平台待办顺带）
- docker-compose.yml 模板（nacos + gateway + bootstrap 三容器编排示例）

### P2（明确不做，下版再说）

- Seata 分布式事务
- 服务级数据库隔离（每模块独立库/独立连接池）
- 多前端工程拆分
- 服务网格/链路追踪（SkyWalking）
- V5.0 M2/M3

## 四、关键设计决策

| 决策点 | 定案 | 理由 |
|---|---|---|
| 第三态 vs 开关 | `'micro'` 独立态，不加 boolean 开关 | 结构差异（五模块、BOM、bootstrap.yml）是目录级的，塞 boolean 会让 multi/micro 组合矩阵失控；三态语义与 V4.4/V4.5/V5.5 三组开关一致 |
| Nacos 依赖开关 | `nacos.enabled` 运行时开关（yml），依赖始终在 classpath | 编译期排除依赖会让「同一产物两栖运行」 impossible；运行时开关零成本降级 |
| Feign 粒度 | 骨架 + 手写约定，不按表自动生成 | 跨服务契约（DTO 归属、事务边界）需要人判断；自动生成是伪需求（等真实反馈） |
| 网关鉴权 | 透传不解析 | 鉴权仍在各服务 AuthContextFilter；网关做路由/跨域即可，M1 不引入网关级 token 校验 |
| Spring Cloud 版本 | 2023.0.x（Leyton）+ spring-cloud-alibaba 2023.0.1.x | 与 Boot 3.2.5 官方兼容矩阵 |

## 七、风险

1. **兼容矩阵**：Spring Cloud / alibaba / Boot 三方版本错一个就启动失败——排期 S6 首日先做「手工最小工程」验证矩阵，再写模板生成（先证矩阵再自动化）。
2. **Nacos 环境波动**：S8 依赖本机 Nacos 存活；AC2 的 false 模式保证无 Nacos 也能全绿验收，Nacos 实测单列 AC3 可降级为手测项。
3. **模板膨胀**：ftl 分支增多（mono/multi/micro 三态），靠基线快照三场景全覆盖防回归——S8 的基线零 diff 是硬门禁。
