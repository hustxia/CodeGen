# 代码生成器 V6.7 规划 —— 产物测试出厂：生成的工程自带可跑通的测试骨架

> 日期：2026-10-28　状态：规划待过目
> 与 V6.1~V6.6 无强耦合，只消费既有开关模式（三态回落）与资源注入模式（scaffold-* 资源目录）。
> 定位：产物质量从「编译过 + 人工冒烟」升级到「**测试随代码一起出厂**」——生成物打开就是 `mvn test` 全绿，商城后续迭代有回归护栏。

## 二、主题与理由

**为什么是它**：

1. **备选池首位，等了两版**。V6.2 规划明确写「产物集成测试骨架（Testcontainers + 生成 controller 集成测试模板）——量级大，值得独立一版」。
2. **真实痛感最高频**：V6.5/V6.6 连续两版各挖 5-6 个坑，全靠手写冒烟脚本兜住；商城实际迭代中，每次在生成物上改代码都是「改完手点一遍」。产物 0 测试意味着**生成的代码越多，不敢动的区域越大**——与代码生成器的价值主张相反。
3. **冒烟工作产品化**：12 个逐版冒烟脚本里反复出现的动作（造登录态、登录后调接口、断言 CRUD、清库）沉淀成产物内的测试模板，以后每版 S8 的 Part B 可以直接跑产物自带测试，不再从零写脚本。
4. **不动主结构**：相比拆 4,725 行单体（顺延了 4 版的候选），本主题只加资源目录 + 一条开关链，风险面小得多，且拆单体的回归恰好可以**用本版的产物测试能力反哺**（拆完跑产物测试证明行为不变）。

**为什么不是别的**：

- 拆 GenScaffoldServiceImpl：债真实但纯内部重构，用户可见价值为零；且拆完仍需等价性证明——不如先有产物测试这个「等价性证明工具」。
- 模板组第二技术栈（Vue3+Vite）：商城用 Vue2，收益在未来；且多栈验证需要先有测试护栏才敢扩。
- 平台可观测性：平台是单人使用的内部工具，运维面板收益偏弱。

## 三、范围

### P0-1 测试基建物料：`scaffold-test/` 资源目录

对齐 `scaffold-file/` 模式（V6.6 刚趟平的路：资源目录 + `__PKG__` 替换 + 每次改资源必须重打包平台 jar）。

| 文件 | 内容 |
|---|---|
| `pomTestDeps.txt`（或直接在 pomJava 方法内注入） | `spring-boot-starter-test`（test scope）+ `com.h2database:h2`（test scope） |
| `application-test.yml` | 测试 profile：H2 `MODE=MySQL;DATABASE_TO_LOWER=TRUE`，`sql.init.mode=always` + `schema-test.sql`（产物 DDL 的 H2 兼容版，与正式 DDL 同源生成） |
| `schema-test.sql.ftl` | 由表清单生成的 H2 兼容建表脚本——**与正式 `db/*.sql` 同一模型产出，防漂移**（V4.4 schema-test 教训的前车之鉴） |
| `LoginStateTestSupport.java` | 测试基类：`@SpringBootTest + @AutoConfigureMockMvc`，`@BeforeAll` 造登录态（直插 token 表，复用 Part B 冒烟已验证的手法），暴露 `mockMvc + tokenHeader` |
| `CrudControllerTest.ftl` | 每业务表一份：list 分页断言 / create→get→update→delete 全链 / 未登录 401。只覆盖 generated 端点，不猜业务逻辑 |

**验收**：新 scaffold 的产物在工作区 `mvn test` 全绿（H2 跑通，无需 Docker/MySQL）；对 demo_goods_file 一主一子场景至少 list/create/update/delete/401 五类断言。

### P0-2 开关链：`sys_project.test_enabled` 三态

完全复制 V6.6 `file_enabled` 模式（已三次验证）：

- DDL：`V6.7__test_enabled.sql`，`tinyint DEFAULT 1 COMMENT '测试骨架:1=生成(默认) 0=不生成'`——**默认 1**（与 file/pay 不同：测试只加 src/test 目录，零运行时侵入，没有「不配置=关」的理由）
- `GenTemplateModel.resolveTest(Integer)` 唯一回落实现；ProjectConfig 加第 11 组件 + 10 参兼容构造
- `SysProjectServiceImpl` 第 5 条显式 SET（V4.4 坑清单）
- 前端 `triStateDefs` 加「测试骨架」项 + `defaultForm` 加字段
- **无侵入证明**：test_enabled=0 的场景基线与旧版逐字节一致；基线测试加 `test()` 场景

**验收**：`mvn -o test` 全绿（基线 10 场景）；test_enabled=0 场景 ZIP 内无 src/test 痕迹。

### P0-3 脚手架接线

- `GenScaffoldServiceImpl` 主流程：testEnabled 时写 `src/test/` 全套（nextSteps 加一条「运行 mvn test」）
- `applicationYml` 不动（测试配置在 test profile，不污染主 yml）——**刻意不学 V6.6 往主 yml 加块**，避免缩进坑复发面
- S8 冒烟 Part B 增加产物内 `mvn test` 实跑断言（产物工程自带测试 = 冒烟脚本直接调它，替代手写登录态部分）

### P1-1 场景覆盖扩展

- 主子表（masterdetail）：子表级联保存/级联删除的集成测试分支
- 树形（tree）：父子查询与 cascadeMode 断言
- 唯一性校验：重复提交 400 断言（P1-3 生成的前端查重 + 后端兜底对齐）

**验收**：三模板分道各出一份集成测试快照进平台基线。

### P2-1 平台自检接线

- lint/自检报告加「产物测试数」字段（`src/test` 文件计数）——顺带补 V6.1 降级项「lint 报流程部署数」同款接线
- AC3 补账：借产物测试骨架的登录态造法，实测 V6.1 审批提交→审批→驳回端到端

## 四、明确不做

| 不做 | 理由 |
|---|---|
| Testcontainers | 产物用户环境不保证有 Docker；H2 MODE=MySQL 够覆盖 generated CRUD；等真实方言撞墙再评估 |
| 前端测试产物（vitest 骨架） | 产物前端是 Vue2+webpack，vitest 配置成本高；后端测试价值密度优先 |
| 覆盖率门禁（JaCoCo 出厂） | 先让测试存在，再谈覆盖率指标；避免「为了覆盖率写断言」 |
| 拆 GenScaffoldServiceImpl | 独立主题（见备选），本版产物测试恰好是未来拆分的等价性证明工具 |
| 逆向工程 | 用户已否（V6.0 规划 2026-10-25 记录），不再进备选池 |

## 八、风险

| 风险 | 缓解 |
|---|---|
| H2 MODE=MySQL 方言差异（datetime/tinyint(1)/中文注释/索引语法） | S0 先做兼容性预检 spike，撞墙清单进坑库；`schema-test.sql.ftl` 与正式 DDL 同模型产出防漂移 |
| 产物测试造登录态依赖 token 表结构（V6.4 持久化方案细节） | LoginStateTestSupport 直插表的手法已被 v66-s8-smoke-b.mjs 验证；TokenStore 表结构变更时测试基类同步改（契约测试守卫） |
| 每表一份测试导致产物文件数膨胀 | 只对 genEntity=1 的业务表生成，主子表只测主表控制器；文件计数进自检报告可见 |
| 基线快照翻倍（10 场景 × 新模板） | test 场景基线只含 testEnabled=1；0 场景复用现有快照断言无 src/test 即可，不新增基线文件 |
| 平台 jar 与资源不同步老坑（V6.6 实测：改 scaffold-test 后必须重打包） | 写进验收清单第 8 项的检查步骤：`unzip -p jar BOOT-INF/classes/scaffold-test/xxx` 核对 |
