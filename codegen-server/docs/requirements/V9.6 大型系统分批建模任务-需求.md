# 代码生成器 V9.6 需求：大型/超大型系统分批建模任务

> 版本：v1.0（2026-11-15）　|　上游：V9.5「AI 建表推荐与人工确认」　|　状态：已实现，待接入真实模型复验

## 一、背景与目标

V9.5 的 AI 建表推荐对 `large` / `huge` 已做「拆模块 → 逐模块建模」，但执行方式是**单次 HTTP 请求内串行循环**：

- 10 个模块 × 单次 5–10 分钟（本地 CPU 8B）= 50–100 分钟，远超浏览器/网关超时，请求必然断开；
- 中途失败即整单丢失，前面的模块白跑，不能续跑；
- 用户看不到任何进度，只能干等；
- 同一时刻只能跑一个任务，机器利用率低。

**目标**：把大型/超大型建模改成「任务 + 批次」的后台执行模型——提交即返回任务号，调度器多 worker 并发跑批次，进度可查、失败可重试、进程重启可续跑。

## 二、功能点

1. **任务化提交**：`POST /gen/ai-build/plan/job`，立即返回 `jobId` 与批次总数，不再占用请求线程。
2. **批次拆分**：第 0 批为 `split`（拆模块），成功后按模块生成 N 个 `module` 批；模块数上限 `moduleCap=40`。
3. **多 worker 并发**：`@Scheduled` 每 2s 扫一次，按空闲 worker 数认领 `pending` 批次；认领用条件更新，天然防重复。
4. **进度可观测**：`GET /gen/ai-build/job/{id}` 返回 `progress / doneBatch / totalBatch / runningBatch / failedBatch / totalTable` 及逐批明细。
5. **结果获取**：`GET /gen/ai-build/job/{id}/result`，仅终态可取；部分失败时返回已成功批次的表，状态标 `partial`。
6. **取消**：`POST /gen/ai-build/job/{id}/cancel`，未开始的批次不再认领。
7. **超时回收与重试**：`running` 超过 `batchTimeoutSeconds`（默认 900s）视为卡死，重置为 `pending` 重试，最多 `maxRetry`（默认 2）次。
8. **重启续跑**：任务与批次落库（`gen_ai_build_job` / `gen_ai_build_batch`），进程重启后调度器继续认领剩余批次。
9. **补表差集沿用**：`scope=supplement` 的已有表清单在提交时固化进 payload，各模块批次建模后统一走差集过滤。

## 三、范围边界

**本期做**：建模（plan）阶段的异步化、批次调度、进度、取消、重试、续跑。

**本期不做**：
- `confirm`（落库 / 建库 / 微服务拆库）仍为同步接口，未纳入批次；超大型建库的异步化留 V9.7。
- 不引入 MQ / 分布式任务框架；单实例内多 worker + 数据库条件更新足够，多实例并存也不会重复执行（认领在 SQL 里完成）。
- 不做 SSE 推送，前端用 2s 轮询。

## 四、阶段与写入边界

| 阶段 | 写什么 | 不写什么 |
|---|---|---|
| 提交 | `gen_ai_build_job` 1 行 + `split` 批次 1 行 | 不写 `gen_table`、不建业务库 |
| 拆模块 | 追加 N 行 `module` 批次，回写 `total_batch` | 不写表结构结果 |
| 模块建模 | 每批写自身 `tables` JSON、`table_count`、状态 | 不改其它批次 |
| 收口 | 汇总去重后的结果写 job `result`，状态置终态 | 不落库成正式表（仍需人工确认） |

## 五、业务规则与异常

- `workerThreads` 不是越大越好：瓶颈在 LLM。云端 API 可 2–4；本地纯 CPU 建议 1，否则互相抢核更慢。
- 单批失败不阻塞其它批；最终 `failedBatch>0 && doneBatch>0` → `partial`，全失败 → `failed`。
- 失败批次保留 `error` 原文，前端可展开看；不静默吞。
- 模块数超 `moduleCap` 时截断并记 WARN，避免误配把任务排到第二天。
- 结果去重口径与 V9.5 同步：跨批次同名表保留首张，补表模式再与已有表做差集。
- 进程被杀留下的 `running` 批次由 `resetStuck()` 回收，不会永久卡住任务。

## 六、验收标准（可观测）

- [x] 超大型（`huge`/`micro`）提交后立即返回 `jobId`，HTTP 不再挂住。
- [x] 批次总数 = 1（split）+ N（模块），进度按批次推进。
- [x] 实测（stub，4 worker）：电商交易系统 → 11 批全部 `success`，70 张表，**8 秒**完成，`progress=100`。
- [x] 结果去重：70 张表 70 个唯一表名；主从/树形关系正常推导（10 主 / 30 从 / 20 单 / 10 树）。
- [x] 故障路径：LLM 不可达时任务落 `failed`，`doneBatch=0`、`totalTable=0`，错误可见。
- [x] 单批超时回收：重试计数递增，超过上限判 `failed` 并收口任务。
- [x] 单测 `AiBuildJobServiceImplTest` 通过；全量测试 0 失败。
- [ ] 真实模型（qwen3:8b / 云端千问）下的批次数与耗时复验——待模型接入。

## 七、版本状态与待确认

已实现并跑通 stub 全链路。待确认两项：

1. 真实模型下单批耗时若超过 900s，`batchTimeoutSeconds` 需要按模型调整（本地 8B 建议 1800）。
2. `confirm` 建库阶段是否也要分批（超大型建库会串行几十个 DDL 会话），建议 V9.7 一并做。
