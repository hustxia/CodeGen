# V9.17 安全加固（P1 backlog 收尾）—— 设计

> 日期：2026-11-24　状态：实现完成（待中央统一验证）
> 承接：`docs/代码生成器-V6.4-规划.md` P1 清单 + `docs/代码生成器-功能全景与版本规划-V9.16.md` V9.17「安全：数据权限 UI、限流、密码策略、单用户互踢」。
> 范围：仅补 V6.4 P1 backlog，不重造 V6.4 已落地的 P0 四件套（token 持久化 / BCrypt 迁移 / 接口权限点后端强制 / 登录防护三件套）。

## 一、背景与现状核对

V6.4 已在生成物里落地「认证鉴权 + 权限闭环」骨架，本轮逐项核对 P1 backlog 的现状与缺口：

| 能力 | V6.4 现状 | 本轮缺口 | 处理 |
|---|---|---|---|
| 数据权限 UI | `DataScopeInterceptor` / `DataScopeRegistry` / `UserContext(DATA_SCOPE,DEPT)` 骨架已有；但生成物 `AuthContextFilter` 从不加载 dataScope，无任何配置入口 | 缺「运行时加载」+「角色配置接口」+「配置页」 | 补齐三环（见 §3.1） |
| 接口限流 | 仅登录限流（IP+账号滑动窗口，AuthController）；**无通用接口限流** | 缺按 IP+接口路径的通用限流 | 在生成物 `AuthContextFilter` 加固定窗口计数（见 §3.2） |
| 密码策略 | `pwdViolation`（长度 / 字母+数字 / 正则）+ 注册、重置密码已接入 | 缺字符类型细分、缺过期提醒、缺「当前用户改密」接口 | 增强校验 + 登录响应过期提示 + `/sysUser/changePwd`（见 §3.3） |
| 单用户互踢 | `kickPreviousSessions` + 4011 被踢响应已完整 | 缺「本次登录踢掉他人」的提示 | `issue()` 回传被踢数，登录响应附 `kickedNotice`（见 §3.4） |

### 生成开关体系现状（关键约束）

- 平台侧生成开关只有 `withAuth`（`GenScaffoldDTO`），在**不可改**的 `GenScaffoldServiceImpl:242` 控制「是否生成整个 auth 包」。平台侧 `GenTemplateSeeder` 把 `gen-templates/*.ftl` 落库，但 `gen-templates/` 下**没有 auth/security 相关 ftl**——认证产物全部是 `ScaffoldAuthWriter` 的**内联字符串**。
- 因此新增能力全部落在 `ScaffoldAuthWriter` 的生成字符串里，随 `withAuth` 一起产出；**`withAuth=false` 时零 diff**（不生成任何相关文件，文件集合不变）。
- 四项能力均为**运行时 `@Value` 开关**（下发到目标工程 `application.yml`），不是生成期开关——这是与现有 V6.4 能力一致的做法，也保证「关闭=零行为 diff」。

### 严格隔离边界

本轮只改：
- `ScaffoldAuthWriter.java`（认证产物内联字符串）
- 平台前端 `codegen-web/src/views/system/data-scope/index.vue`（新增安全配置页）、`.../system/role/index.vue`（加入口按钮）

**未改且不可改**：`ScaffoldCommonWriter.java`（本轮无需改动）、`ScaffoldPomWriter.java`（application.yml 模板）、`GenScaffoldDTO.java`、`GenScaffoldServiceImpl.java`、`ScaffoldSeedWriter.java`（seed SQL）、`pom.xml`、`docs/sql/`、`scripts/`、其它 Writer / 模板。

## 二、总体设计原则

1. **零 diff 契约**：所有新能力默认不产物行为变化（详见 §4）。V6.4 既有产物的字节与断言全部保持。
2. **fail-safe**：数据权限加载失败一律降级 `self`（最小权限），不放大可见范围。
3. **容错优先**：新增配置接口在「目标库未加列 / 未建表」时返回明确提示或空结果，而不是 500。
4. **零第三方依赖**：限流用 JDK `ConcurrentHashMap` 固定窗口计数，不引 Redis / Guava / Bucket4j。

## 三、各能力实现方案

### 3.1 数据权限 UI（生成物后端 + 平台配置页）

**三段闭环：**

1. **运行时加载**（`authContextFilterJava`）：用户鉴权通过后，用 `loadDataScope(userId)` 从 `sys_role.data_scope`（多角色取最宽 `all > dept > self`）与 `sys_user.dept_id` 填充 `UserContext`。表 / 列缺失时 catch 降级 `self` —— 因此**基线产物不改表也安全可用**（所有人都 `self`，只是看不到全量）。
2. **配置接口**（`sysRoleControllerJava`）：
   - `POST /sysRole/dataScope` `{roleId}` → 读 `{dataScope, deptIds}`（缺列缺表返回 `self` / `[]`）
   - `POST /sysRole/assignDataScope` `{roleId, dataScope, deptIds}` → 校验枚举后写 `sys_role.data_scope` 与 `sys_role_dept`
   - `POST /sysRole/dept/list` → 部门树下拉（无 `sys_dept` 表返回空数组，前端可手输 ID）
   - 三个端点已在 `sysApiPermsJava` 挂权限点（读 = `sys_role:list`，写 = `sys_role:assign`），admin 直通。
3. **配置页**（平台前端）：`views/system/data-scope/index.vue`（新增），角色列表 → 范围单选（全部 / 本部门 / 仅本人 / 自定义部门）+ 部门勾选 / 手输；`role/index.vue` 加「数据权限」入口按钮。接口路径与生成物后端对齐，故可整体拷入目标工程前端使用；平台未注册路由 / 端点时优雅降级并提示。

**`custom` 范围说明**：配置层允许选部门并落 `sys_role_dept`；SQL 拦截层（`DataScopeInterceptor`，V6.4 骨架）最初只支持 `self` / `dept` 两种推导。多部门 `IN` 过滤已在后续补齐（见 §8.1）：`loadDataScope` 读取 `sys_role_dept` 写入 `UserContext.deptIds`，拦截器对 `dept` 列登记的表追加 `IN` 条件；空列表回落 `self`。

### 3.2 接口限流（生成物 AuthContextFilter）

- 开关：`auth.api-rate-limit.enabled`（**默认 false，关闭**）。
- 参数：`auth.api-rate-limit.max-requests`（默认 120）、`auth.api-rate-limit.window-seconds`（默认 60）。
- 算法：固定窗口计数，key = `clientIp|METHOD /path`（`X-Forwarded-For` 优先），`ConcurrentHashMap<String, RateWindow>`；窗口滚动靠比较 `start`，超 1 万 key 触发过期清理。
- 超限：HTTP 429 + `Retry-After` + 业务码 429 + 剩余秒数。
- 位置：在 CORS 预检放行之后、token 解析之前执行；白名单（登录 / 健康检查）也经过计数，但默认关闭不改变任何行为。

### 3.3 密码策略（生成物）

- 强度校验（`sysUserControllerJava.pwdViolation`）在既有「长度 / 字母+数字 / 正则」之上新增 4 个开关，默认全 false：
  - `auth.password-policy.require-uppercase`（大写）
  - `auth.password-policy.require-lowercase`（小写）
  - `auth.password-policy.require-digit`（数字）
  - `auth.password-policy.require-special`（特殊字符）
- 过期提醒：`auth.password-policy.expire-days`（**默认 0 = 关闭**）。开启后 `/auth/login` 成功响应附加 `passwordExpired` + `passwordExpireNotice`（基于 `sys_user.update_time`；老库无该列时 catch 不阻断）。
- 当前用户改密：`POST /sysUser/changePwd` `{oldPassword, newPassword}`，从 `UserContext` 取当前用户、校验旧密码（bcrypt / sha256 兼容分派）、走同一套强度策略。权限点映射为空串（仅登录即可）。

### 3.4 单用户互踢增强（生成物）

- `TokenStore.issue(username, ip)` 替代原 `create` 作为签发入口（原 `create` 保留，委托 `issue`，兼容既有调用）；`kickPreviousSessions` 改为返回被踢旧会话数。
- 登录响应在互踢数 > 0 时附加 `kickedNotice`（「本次登录已使 N 个其他设备下线」）。
- 被踢端继续走 V6.4 的 401 + 业务码 4011（`writeKicked`），本次不改。
- **默认状态**：`auth.kick-enabled` 由 `ScaffoldPomWriter.applicationYml` 下发 `true`（默认开启）。互踢会改变行为（多端在线 → 单端），破坏性在 §5 / §6 说明；关闭方式 = 目标工程 yml 设 `auth.kick-enabled: false`。因 `ScaffoldPomWriter` 不在本轮允许改动清单，**本轮未把默认改为 false**。

## 四、零 diff 契约与验证方法

### 4.1 契约定义

| 场景 | 预期 |
|---|---|
| `withAuth=false` | 不生成任何 auth 相关文件，产物文件集合与改动前逐字节一致 |
| `withAuth=true` + 所有新开关默认 | 登录 / 鉴权 / 权限行为与 V6.4 基线一致；新增接口存在但默认不改变既有流程 |
| 关闭某项新能力 | 通过 yml 开关关闭后，该能力运行时行为 = 改动前 |

### 4.2 默认开 / 关一览

| 能力 | 开关 | 默认 | 说明 |
|---|---|---|---|
| 接口限流 | `auth.api-rate-limit.enabled` | **关** | 开才计数 |
| 数据范围加载 | 无开关（随鉴权生效） | 生效但降级 self | 无 data_scope 列时等价「仅本人」，不放大权限 |
| 密码强度（新类型） | 4 个 `require-*` | **关** | 与基线一致 |
| 密码过期提醒 | `auth.password-policy.expire-days` | **关（0）** | 开才附加提示 |
| 单用户互踢 | `auth.kick-enabled` | **开** | V6.4 yml 锁定 true，可配 false 关 |

### 4.3 验证方法（不跑 mvn，由中央统一验证）

1. **静态产物断言**（沿用 `GenV64SecurityHardeningTest` 风格，纯函数不连库）：
   - `authContextFilterJava` 含 `api-rate-limit.enabled:false`、`tryAcquire`、`writeTooManyRequests`、`RateWindow`；
   - 含 `loadDataScope` 且失败分支 `setDataScope("self")`；
   - `sysRoleControllerJava` 含 `dataScope` / `assignDataScope` / `dept/list` 三端点；
   - `sysUserControllerJava` 含 4 个新开关 + `changePwd`；
   - `authControllerJava` 含 `issued.kickedSessions()` / `kickedNotice` / `passwordExpired`。
2. **黄金基线**：`src/test/resources/gen-baseline/` 只锁 13 个 FTL 模板产物，不含认证基座——本轮未改任何 FTL，该基线零 diff。
3. **语法自检**：把各 `static String xxx(pkg)` 的字符串拼接求值后交 `javac -proc:none` 检查，13 个产物类 + AuthContextFilter 全部语法通过（本轮已本地执行）。
4. **既有测试不回退**：`GenV64SecurityHardeningTest` 的全部断言字符串本轮逐一核对仍存在（互踢默认 true、2 处 `fail(pwdViolation)`、4011、滑动窗口等）。

## 五、破坏性影响说明

1. **单用户互踢（默认开启）**：V6.4 起产物默认 `kick-enabled: true`，同账号新登录会使旧 token 立即失效（401/4011）。这对「多端在线」是行为改变。本轮**未改默认值**（受 `ScaffoldPomWriter` 不可改约束），如需恢复多端在线须在目标工程显式配置 `auth.kick-enabled: false`。
2. **数据范围加载**：新增后，所有登录请求都会查 `sys_role.data_scope` / `sys_user.dept_id`（各一次，try-catch）。表结构未升级时查询失败降级 `self`——**不会报错，但表现为「用户只能看本人数据」**。若既有系统是「登录后看全量」，升级到本产物后需按 §6 为角色配置 `all` 或加列。
3. **接口限流 / 密码过期 / 新强度类型**：默认全关，无行为影响。
4. **新增接口**：`/sysRole/dataScope` 等 4 个端点默认对 admin 开放（直通）；普通角色需授予 `sys_role:list` / `sys_role:assign` 权限点。

## 六、未尽事项与风险

1. **互踢默认仍为开**：受严格隔离约束（`ScaffoldPomWriter.applicationYml` 不可改），未把默认改为 false。若产品要求「默认可关=默认关闭」，需单独提改动单放开该文件。
2. **数据权限建表 DDL 未随产物下发**：`sys_role.data_scope`、`sys_user.dept_id`、`sys_role_dept`、`sys_dept` 的建表 / 加列需业务方按实际库执行（不在 `docs/sql/` 允许范围，且 seedSql 不可改）。配置接口已容错，缺表不 500。
3. **`custom` 范围的 SQL 过滤**：配置层已支持多部门落库，但 `DataScopeInterceptor`（V6.4 骨架）仅实现 self/dept 推导，多部门 `IN (...)` 过滤需后续扩展。**→ 已补齐，见 §8.1。**
4. **限流计数器非分布式**：固定窗口计数在单实例内存；多实例部署需外部化（Redis），本轮按「轻量、零依赖」目标未引入。**→ 提供零依赖扩展点 + 外化方案说明，见 §8.2。**
5. **平台侧配置页路由**：平台前端路由由 `sys_menu` 动态注册，`/system/data-scope` 需平台侧登记菜单才可从导航直达；角色页入口按钮已做路由缺失容错（静默提示），不影响既有功能。
6. **前端页面接线**：配置页直接 `import request from '@/utils/request'` 并调用 `/sysRole/*`；目标工程需提供同路径后端（本轮生成物已产出），否则页面走容错提示。

## 八、未尽事项补齐（2026-11-25）

### 8.1 `custom` 多部门 SQL 过滤

- **加载侧**（`ScaffoldAuthWriter.authContextFilterJava.loadDataScope`）：`widest()` 增加 `custom`（优先级 `all > dept > custom > self`，保证既有 self/dept 判定逐字节不变）。当且仅当最终范围为 `custom` 时，联查 `sys_role_dept` + `sys_role(data_scope='custom')` + `sys_user_role` 读取当前用户的多部门 ID，数字白名单过滤后写入 `UserContext.deptIds`；缺表 / 空列表 / 异常一律 `setDataScope("self")`。
- **拦截侧**（`ScaffoldCommonWriter.dataScopeInterceptorJava`）：对 `rule.scope() == "dept"` 且用户范围为 `custom` 的表，用 JSQLParser `InExpression` + 类型化 `LongValue` 节点生成 `dept_id IN (1,2,...)`；表名 / 列名来自生成期固化的 `DataScopeRegistry.register(...)`，运行期只传入数字值，无字符串拼接。空列表回落按本人（`user_id`）过滤。self / dept 既有分支未改动。
- **服务层接线**：`DataScopeInterceptor.applyCustom(LambdaQueryWrapper<T>, SFunction<T,?>)` 提供 `LambdaQueryWrapper.in()` 版本（列由方法引用固化、ID 作为参数绑定），供绕过 MyBatis-Plus 拦截器的自定义查询显式调用；标准 CRUD 由拦截器自动覆盖。
- **取舍说明**：`InnerInterceptor` 工作在「已生成 SQL 的 AST 改写」阶段，无法调用面向新查询构建的 `LambdaQueryWrapper.in()`；因此默认路径采用等价安全的类型化 `LongValue` 节点（值来自 `Long` 白名单，零字符串拼接），显式路径才用 `.in()`。

### 8.2 限流计数器外化（零依赖扩展点）

- **实现**：生成物 `AuthContextFilter` 内新增 `public interface RateLimitCounter { long tryAcquire(String key, int maxRequests, long windowSeconds); }` 与默认 `InMemoryRateLimitCounter`（原固定窗口逻辑逐行搬入，行为不变）。过滤器以 `@Autowired(required = false)` 注入该接口，未注册实现时使用内存默认——关闭外化时行为与改动前一致。
- **未生成 Redis 实现类的理由**：`@ConditionalOnBean(RedisTemplate.class)` 需要在编译期硬引用 `RedisTemplate`，会迫使生成物引入 `spring-boot-starter-data-redis`，违反零第三方依赖约束；改用反射调用 Spring Data Redis API 虽可编译通过，但方法签名随 Spring Data Redis 版本漂移、脆弱且难维护，属于「坏代码」。因此**不生成 Redis 类**，改为在生成物 `application.yml` 的 `auth` 段给出可直接照做的注释方案：业务方自行加 starter、实现上述接口注册为 bean，用 `RedisTemplate.execute(Lua)` 完成 `INCR` + `EXPIRE` 原子计数，超限用 `PTTL` 换算剩余秒数。
- **原子性取舍**：采用 Lua 单脚本而非 `INCR` + `EXPIRE` 两步——两步之间若进程崩溃会留下无 TTL 的 key，导致该 IP/路径被永久限流；Lua 把两步合并为 Redis 侧原子操作。
- **零 diff 契约**：未注册外部实现时，API 限流仍是原来的 `ConcurrentHashMap` 固定窗口；登录限流（IP+账号滑动窗口）未改动。
