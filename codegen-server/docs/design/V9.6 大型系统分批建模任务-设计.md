# 代码生成器 V9.6 设计：大型/超大型系统分批建模任务

> 版本：v1.0（2026-11-15）　|　依赖：V9.5 `AiTableRecommendServiceImpl`（建模逻辑不改，只复用）　|　需求：`docs/requirements/V9.6 大型系统分批建模任务-需求.md`

## 一、定位与边界

V9.6 是 V9.5 `plan()` 的**异步执行层**，解决「大型/超大型单请求串行建模必超时」的问题。

- **只接管建模阶段**：`split`（拆模块）+ 逐模块 `model`。
- **不改建模语义**：prompt 拼装、已有表约束、跨模块去重、补表差集，全部复用 V9.5 已有方法（`withExistingHint` / `loadExistingTableNames` / 去重逻辑），因此小系统仍走原同步链路，两条路径结果口径一致。
- **不改 V9.4/V9.5 现有类**（`AiTableRecommendServiceImpl` 仅改为 `public` 暴露复用点，未改行为）。

```
前端 ──POST /plan/job──► AiBuildJobServiceImpl.submitPlan   （落 job + split 批次，立刻返回）
                              │
        AiBuildJobScheduler.tick()  每 2s
                              │  ① resetStuck()  回收超时 running
                              │  ② dispatch(free) 条件更新认领 pending
                              ▼
                    ThreadPool(workerThreads) ──► runBatch
                              │
              split  → aiModelService.modules() → 插 N 个 module 批次
              module → aiModelService.model()  → 写本批 tables
                              │
                      finalizeIfDone → 汇总去重 → job.result + 终态
```

## 二、表结构

`docs/sql/V9.6__ai_build_job.sql`（幂等，`CREATE TABLE IF NOT EXISTS`）：

| 表 | 作用 | 关键列 |
|---|---|---|
| `gen_ai_build_job` | 任务主表 | `job_no` 唯一、`status`、`total_batch/done_batch/failed_batch/total_table`、`payload`（dto+已有表）、`result`（最终 JSON）、`error` |
| `gen_ai_build_batch` | 批次表 | `job_id+seq`、`kind`（split/module/confirm）、`module_name`、`status`、`retry_count`、`tables`（本批表结构 JSON）、`pipeline_id`、`started_at/finished_at` |

`pipeline_id` 预留给后续把 `confirm` 建库也批次化时，关联每条流水线。

## 三、核心模型

- `GenAiBuildJob`：任务聚合根；`payload` 存 `Payload{dto, existing, descForAi, relevanceWarning, relevanceTip}`，避免重跑时重新读库、也保证续跑语义稳定。
- `GenAiBuildJobBatch`：一次 LLM 调用的执行单元，状态与结果自治；`tables` 是该批产出的 JSON，收口时统一解析。
- `GenAiBuildJobVO`：前端视图，含 `progress`（`(done+failed)/total` 百分比）与 `batches[]` 明细。
- `AiBuildJobProperties`（`gen.ai-build.job.*`）：`enabled / workerThreads / intervalMs / batchTimeoutSeconds / maxRetry / moduleCap`。

## 四、流程与状态

**任务状态机**：`pending → running → success | partial | failed`，任意时刻可 `canceled`。

**批次状态机**：`pending → running → success | failed`；`skipped` 预留给取消后未执行的批次。

收口规则（`finalizeIfDone`）：

1. 同任务仍有 `pending/running` 批次 → 直接返回，不提前宣告完成；
2. 全部结束 → 解析各 `module` 批次的 `tables`，按表名去重（保留首张）；
3. `failedBatch==0` → `success`；`failedBatch>0 && 有成功批次` → `partial`；全失败 → `failed`；
4. 补表模式再与 `payload.existing` 做差集，写回 `result`。

## 五、后端设计

| 方法 | 职责 | 关键点 |
|---|---|---|
| `submitPlan(dto)` | 参数校验（AI 开关、系统名、补表必带 projectId）、固化 payload、落 job + split 批 | 不在请求线程内做任何建模 |
| `dispatch(max)` | 统计 `running` 数算空闲位，取 `pending` 候选，**条件更新** `where id=? and status='pending'` 认领 | 认领成功才提交线程池，多实例并存不会重复执行 |
| `runBatch(id)` | 按 `kind` 分发 `doSplit` / `doModule`，异常统一写 `error` + `failed` | 单批失败不影响其它批 |
| `resetStuck()` | `running` 且 `started_at` 超时 → 未达重试上限回 `pending`，达上限判 `failed` | 覆盖进程被杀 / 连接挂死 |
| `finalizeIfDone(id)` | 收口、去重、差集、写终态 | 幂等：已是终态直接返回 |

**并发控制**：`ThreadPoolExecutor`（固定线程数，命名 `ai-build-N`，守护线程）；`AiBuildJobScheduler.tick()` 用 `AtomicBoolean` 串行化，防止上一轮认领未结束下一轮重复提交。

## 六、前端设计

`src/views/gen/aibuild/index.vue`：

- `scale ∈ {large, huge}` → 调 `/plan/job`，否则仍走同步 `/plan`；
- 提交后显示「后台进度」区：`el-progress` + `批次 x/y · 已出表 n 张 · 状态`，可展开逐批明细（模块名/状态/表数/错误）；
- 每 2s 轮询 `GET /job/{id}`，终态后 `GET /job/{id}/result` 并复用 `applyPlan()`（与同步路径同一套渲染）；
- `partial` 时提示「部分模块失败，已用成功批次的表」，不伪装成功；
- 运行中可「取消任务」。

## 七、安全与配置

- 接口沿用现有 JWT 过滤器（`AuthContextFilter`），未登录 401；**注**：本平台尚无接口级权限注解，这是已知缺口（见项目评估），V9.6 未扩大该缺口，但也没有修复它。
- 任务只能由创建者所在租户可见？当前无租户隔离，按「登录即可见 jobId」处理，jobId 为雪花 ID（不可枚举）。
- 本地纯 CPU 建议 `worker-threads: 1`（并发只会抢核），云端 API 建议 2–4。

## 八、测试

- 单测 `AiBuildJobServiceImplTest`（4 例，Mockito，不启 Spring）：提交落库与 payload、超时回收两条分支、收口合并与 `partial`、存在未完成批次时不提前收口。
- 测试环境 `gen.ai-build.job.enabled=false`：避免每个 `@SpringBootTest` 拉起调度线程刷「表不存在」噪音；`schema-test.sql` 同步补两表结构。
- 实测（stub，4 worker）：电商交易系统 → 11 批全 success / 70 表 / 8s / `progress=100`，70 个表名唯一，关系推导 10 主 30 从 20 单 10 树。
- 故障实测：stub 不可达时任务 `failed`（`doneBatch=0`、`totalTable=0`），错误原文落 `error`。
