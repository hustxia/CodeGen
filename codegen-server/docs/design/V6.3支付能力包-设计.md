# V6.3 支付能力包 设计

> 日期：2026-10-25　需求：docs/requirements/V6.3支付能力包-需求.md

## 一、表结构

```sql
-- V6.3__pay_enabled.sql（平台库）
ALTER TABLE sys_project
    ADD COLUMN pay_enabled tinyint DEFAULT NULL COMMENT '支付能力包:NULL=未配置(关) 1=生成 0=不生成' AFTER default_gen_deploy;

-- 产物库 db/pay.sql（scaffold 生成，pay_enabled 开启时）
CREATE TABLE IF NOT EXISTS pay_order (
    id             bigint       NOT NULL AUTO_INCREMENT COMMENT '主键',
    out_trade_no   varchar(64)  NOT NULL COMMENT '商户单号（幂等键）',
    subject        varchar(128) NOT NULL COMMENT '订单标题',
    amount         bigint       NOT NULL COMMENT '金额：分',
    pay_channel    varchar(16)  DEFAULT NULL COMMENT '渠道：mock/wxpay/alipay',
    pay_status     tinyint      NOT NULL DEFAULT 0 COMMENT '0待支付 1成功 2关闭 3退款',
    business_type  varchar(64)  DEFAULT NULL COMMENT '业务表名（联动 pay_status）',
    business_id    bigint       DEFAULT NULL COMMENT '业务主键',
    notify_raw     mediumtext   COMMENT '回调原始报文（审计）',
    paid_at        datetime     DEFAULT NULL COMMENT '支付成功时间',
    deleted        tinyint      NOT NULL DEFAULT 0,
    create_by      bigint       DEFAULT NULL,
    create_time    datetime     DEFAULT NULL,
    update_by      bigint       DEFAULT NULL,
    update_time    datetime     DEFAULT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_out_trade_no (out_trade_no)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='支付单';
```

schema-test.sql 同步：sys_project 补 pay_enabled 列（V4.4 教训：加列后必须同步，否则契约测试 Unknown column 全红）。

## 二、功能设计（实施态）

| 编号 | 功能点 | 实施要点 |
|---|---|---|
| F-01 | 开关与回落 | `pay_enabled` 可空三态；回落唯一实现 `GenTemplateModel.resolvePay`（项目级 → 硬编码 0），同 resolveGenDeploy 先例；`GenScaffoldDTO` +payEnabled；`SysProject` +payEnabled（update 尾部显式 SET，三态坑同款） |
| F-02 | pay_order | 见上 DDL；进 scaffold `db/pay.sql`；PipelineExecutor seed 后导入 |
| F-03 | PaymentService 抽象 | 接口：`create(subject, amountFen, businessType, businessId) → PayOrder`（内部落库+渠道下单，回填 payUrl/qrContent 到返回 VO）；`query(outTradeNo)`；`close(outTradeNo)`；`markPaid(outTradeNo, channelAmountFen, raw)` —— **唯一状态流转入口**：`UPDATE pay_order SET pay_status=1, paid_at=NOW() WHERE out_trade_no=? AND pay_status=0` 影响行数=1 才联动业务+返回成功（幂等核心） |
| F-04 | 三实现 | `MockPayService`：create 直接返回 mock 支付 URL；`WxPayNativeService`：wechatpay-java NativeService 下单取 code_url（验签用 NotificationParser）；`AliPayPageService`：alipay-sdk page.pay 返回表单/URL（RSA2 验签）；渠道实现按 yml `pay.channel` 单选，缺省 mock |
| F-05 | mock 支付端点 | `POST /pay/mock/{outTradeNo}/pay` —— 运行时校验 `pay.channel=mock` 否则 404；模拟渠道回调：读单→金额校验→markPaid（与真渠道同构） |
| F-06 | 业务联动 | markPaid 成功后：business_type 过白名单正则 `^[a-z][a-z0-9_]{0,63}$` + information_schema 表存在性校验 + 业务表含 pay_status 列才执行 `UPDATE {table} SET pay_status=1 WHERE id=?`（JdbcTemplate，动态表名只走白名单校验结果，防注入） |
| F-07 | 回调端点 | `POST /pay/notify/{channel}`：wxpay→NotificationParser 验签→金额二次校验→markPaid→返 `{"code":"SUCCESS"}`；alipay→RSA2 公钥验签→同链路→返 `success`；验签失败 401；幂等由 markPaid 保证（重复回调影响行数=0） |
| F-08 | 查单补偿 | `PayReconcileJob`：@Scheduled(fixedDelayString=`${pay.reconcile-interval-ms:300000}`)，yml `pay.reconcile-enabled:true` 开关；扫 pay_status=0 且超 1 分钟的单，逐单调渠道 query 收状态 |
| F-09 | 收银台 | `views/pay/cashier.vue`：路由 `/pay/cashier/:outTradeNo`；金额展示分→元；qrcode 库前端出码（wxpay 用 code_url）；轮询查单 2s；成功跳转 `redirect` 参数页 |
| F-10 | 支付记录 | `views/pay/order.vue`：复用 vuePage 样式体系，状态徽标 + 关单/查单按钮；api `src/api/pay.js` |
| F-11 | 业务接入约定 | 模板条件块：业务表含 pay_status 列时详情页加「去支付」按钮 → 跳收银台（下单传 business_type/business_id） |
| F-12 | 前端注入 | `GenTemplateEngine.renderPayShared`：resolvePay=1 时注入 api/pay.js、views/pay/cashier.vue、views/pay/order.vue、pay-router-snippet.txt（同 renderFlowShared 先例）；scaffold 的 package.json +qrcode 依赖 |

## 三、接口设计（产物侧）

| 接口 | 方法 | 路径 | 请求体 | 响应 |
|---|---|---|---|---|
| 下单 | POST | /pay/order | `{subject, amount, businessType?, businessId?, redirect?}`（amount 元，后端转分） | `data:{outTradeNo, payUrl, qrContent?}` |
| mock 支付 | POST | /pay/mock/{outTradeNo}/pay | — | 同真渠道回调效果 |
| 渠道回调 | POST | /pay/notify/{channel} | 渠道报文 | wxpay: `{"code":"SUCCESS"}`；alipay: `success` 文本 |
| 查单 | GET | /pay/order/{outTradeNo} | — | `data:{payStatus, paidAt, amount}` |
| 关单 | POST | /pay/close/{outTradeNo} | — | `{code,msg}` |

平台侧零新增接口（pay_enabled 走既有系统 CRUD）。

## 四、关键设计决策

| 决策点 | 定案 | 理由 |
|---|---|---|
| 开关形态 | 可空三态 + resolvePay 硬编码 0 | V4.4 坑库教训：NOT NULL DEFAULT 杀死未来回落层；语义与规划「缺省 0」等价 |
| 状态流转 | markPaid 唯一入口，条件 UPDATE 幂等 | 回调重放/mock 重复支付/补偿任务三路并发天然安全，不依赖分布式锁 |
| 业务联动 | business_type 白名单+表存在性校验后动态 UPDATE | 满足 AC2 联动验收；动态表名必须过校验，字符串拼接前先过正则+information_schema |
| 二维码 | 前端 qrcode 出码 | 后端零图像依赖；code_url 本就是文本 |
| SDK 风险 | 两 SDK 均中央仓库直供 | V6.1 坑 43b（Alfresco 私仓）不复现；产物离线编译需先在线拉一次 |
| mock 语义 | 独立端点走 markPaid 同构链路 | 与真渠道测试等价；mock 端点运行时校验渠道，真渠道下自动失效 |
| 代码注入方式 | GenScaffoldServiceImpl 字符串块（V6.1 Flow 基座先例） | 系统级模块不挂表模型，与 flowServiceJava 等同模式；FTL 仅用于业务表接入条件块 |
