## 一、定案（相对规划的实施级细化）

| 决策点 | 定案 | 与规划的差异 |
|---|---|---|
| 开关 | `sys_project.mobile_enabled` 可空三态（NULL/0=关，1=开）；回落唯一实现 `GenTemplateModel.resolveMobile`，语义同 `resolvePay`（V6.3 同款模式：系统级能力包，无表级开关） | 无 |
| 工程形态 | 独立 uni-app 工程 `{frontendModule}-mobile`（与 `{frontendModule}` 平级）；uni-app Vue3 语法 + vite + uni-ui + pinia | 无；模块名从 frontendModule 推导，不加新列 |
| **页面生成** | **通用动态页三件（list/detail/form）+ 每表声明式配置文件**，不用「按表出整页模板」 | **实施定案调整**，理由见下节 |
| 产物落位 | 表产物 relPath 前缀 `mobile/` = 第三侧 MOBILE；写盘 root = 前端容器根 + `{frontendModule}-mobile`；ZIP 原样携带 `mobile/` 前缀 | relPath 契约新增第三侧 |
| 模板载体 | 每表配置文件走 **Java 生成器方法**（`mobileTableConfigJs`，V6.4 `apiPermsJava` 同款），**不进 gen_template 库** | 避开「库模板优先于 classpath，改 ftl 不生效要同步改库」的老坑 |
| 流水线 | 新步 `package_mobile`：npm install（幂等）+ `build:h5` + `build:mp-weixin`；CI 只出包不发布 | 无 |
| 登录体系 | 复用 /auth/login + Bearer，M1 不做 wx.login | 无 |
| 待办页 | todo.vue 调 /flow/todo，接口异常/未实装显示占位，不阻断 | 无（V6.1 builtin 流程已实装，直接可用） |

### 动态页方案的理由（对规划 P0-2 的替代）

规划原定「mobileList/Detail/Form 三件模板按表出整页」。实施时发现 uni-app 的 `pages.json` 是**静态注册制**：按表出页就必须在生成期维护 pages.json 片段——等于再造一个 gen-routes.js 的维护链（GenMenuServiceImpl 那套），平台侧还要同步建移动菜单，M1 成本翻倍且引入新的漂移面。

动态页方案：三件通用页面在 scaffold 静态注册（pages.json 恒定），每张表只出一份**声明式配置 JS**（字段中文名/控件类型/枚举映射/必填/接口路径），`import.meta.glob` 自动聚合、首页自动出业务入口——**新增表零注册、零重建 pages.json**。控件映射逻辑收敛一处（动态页组件内），与规划「复用 GenTemplateModel 现有列分类标记」的意图一致。规划验收标准（登录→列表→详情→表单→提交、字典列显标签、控件类型正确）不受影响。

### 2.2 每表配置文件（生成侧，Java 方法出）

- relPath：`mobile/src/config/tables/{moduleName}/{tableName}.js`
- 出表条件：`resolveMobile=1` && genFrontend && genVuePage && 非从表（masterTableId 为空）——树表 M1 也排除（无成熟移动形态，规划口径）

- 列分类复用 `GenTemplateModel` 现有标记（javaType/enumMap/commentLabel），不新增模型
