## 三、数据结构

### 3.1 节点状态（流程图数据源）

`/flow/state`（即 `getFlowProgress`）在原有 `flowCode / flowName / status / nodes / actions` 上**追加** `nodeStatuses`：

```js
nodeStatuses: [
  {
    nodeKey:     '0_1',            // from + '_' + to，前端 v-for key
    nodeName:    '主管审批',
    order:       1,
    status:      'DONE',           // DONE | CURRENT | DELEGATED | REJECTED | PENDING
    assigneeName:'张三',
    finishTime:  '2026-11-24 10:12:33'
  }
]
```

后端来源（两引擎共用同一份 `sys_flow_task` 投影逻辑）：

- `DONE`：`to_status = 当前节点 from` 且 `action ∈ (SUBMIT, APPROVE, COUNTERSIGN_RESULT)`
- `CURRENT`：`from = 业务表当前状态`
- `REJECTED` / `DELEGATED`：该节点存在 `REJECT` / `DELEGATE` 流水且非当前节点
- `PENDING`：其余节点
- `bizId == null` 时返回空数组（草稿预览不画图）

### 3.2 会签意见（对齐 `approval_node` 模型）

智慧村务模板 `approval_node` 的列语义：`approval_id / node_name / node_order / assignee_id / status / result / comment / handle_time`。产物侧不新建表，用 `sys_flow_task` 同构投影：

| approval_node 语义 | 产物侧 `sys_flow_task` 承载 |
|---|---|
| `node_name` / `node_order` | `from_status`（当前节点）/ 节点在 `def.nodes` 中的序号 |
| `assignee_id` | `oper_user_id` |
| `status` / `result` | `action`：`COUNTERSIGN_AGREE` / `COUNTERSIGN_REJECT` |
| `comment` | `comment`（「会签同意/反对：<意见>」） |
| `handle_time` | `oper_time` |

`/flow/countersign/opinions` 返回 `[{ assigneeId, assigneeName, result: '同意'|'反对', comment, handleTime }]`，与前端表格列一一对应。

### 3.3 委派留痕

委派写两条流水，均用现有列，零 DDL：

1. `action = 'DELEGATE'`，`oper_user_id` = 原审批人，`to_status` = 新审批人 ID，`comment` = `委派给 {id}({name})；原因：{reason}`
2. `action = 'DELEGATE_ASSIGN'`，`oper_user_id` = 新审批人，表示接收转办（便于「已办」列表留痕）

`nodeStatuses` 里承载 `DELEGATED` 状态；`/flow/records` 兼容视图自动包含这两条记录。

### 3.4 流程定义 JSON（设计器输入）

```json
{
  "flowCode": "hr_leave_flow",
  "flowName": "请假审批",
  "tableName": "hr_leave",
  "statusCol": "status",
  "nodes": [
    { "from": "0", "to": "1", "nodeName": "主管审批", "roleCode": "manager",
      "rejectTo": "0", "countersignMode": "ALL", "approvers": [2, 3],
      "condition": "amount>1000" }
  ]
}
```

`countersignMode`：`SINGLE`（默认，普通审批）/ `ALL`（全部同意）/ `ANY`（一人同意）/ `VETO`（一票否决）。
`approvers` 可选；不配时投票人取当前登录用户。

## 四、新增接口（产物侧，全部挂在既有 `FlowController`）

| 接口 | 方法 | 路径 | 请求体 | 响应 |
|---|---|---|---|---|
| 流程进度（既有端点扩展） | GET | `/flow/state?flowCode=&bizId=` | — | `data` 追加 `nodeStatuses` |
| 会签投票 | POST | `/flow/countersign` | `{flowCode,bizId,approvers[],mode,comment,approved}` | `{code,msg,data:null}` |
| 会签意见 | GET | `/flow/countersign/opinions` | `flowCode,bizId,nodeName?` | `data:[会签意见]` |
| 委派（转办） | POST | `/flow/delegate` | `{flowCode,bizId,toUserId,toUserName,reason}` | `{code,msg,data:null}` |
| 定义校验 | POST | `/flow/def/validate` | `{defJson}` | `data:{valid,errors[],normalized[]}` |
| 定义保存 | POST | `/flow/def/save` | `{defJson}` | `{code,msg,data:null}` |

实现位置（均在 `ScaffoldFlowWriter.java` 生成的字符串中）：

- `FlowService`：`countersign` / `countersignOpinions` / `delegate` / `validateDef` / `saveDef` 为 **default 方法**（第三方实现不因升级编译断裂）
- `BuiltinFlowService` / `ActivitiFlowService`：各自 override；builtin 全走 `JdbcTemplate`，activiti 的会签结果复用 `complete()` 走引擎网关，委派调用 `taskService.setAssignee`，定义校验/保存两引擎共用同一套 JDBC 逻辑
- 安全：`flowCode` / `tableName` / `statusCol` 均过 `[A-Za-z0-9_]` 白名单（沿用 V6.1 `IDENT`），SQL 参数一律占位符，设计器保存不写 `bpmn_xml`（不破坏 Activiti 部署幂等 hash）

### 会签判定规则

| mode | 通过条件 | 不通过行为 |
|---|---|---|
| `ALL` | 反对票 0 且同意票 ≥ 应到人数（取节点 `approvers.length`，未配则取本轮投票人数） | 立即驳回 |
| `VETO` | 同 ALL（任一反对即否决，可配置的「一票否决」） | 立即驳回 |
| `ANY` | 同意票 ≥ 1 | 若尚无同意票则**继续等待**，不驳回 |

结果写一条 `action = 'COUNTERSIGN_RESULT'` 流水并推进业务状态列；activiti 同步经网关推进引擎实例。

## 五、前端组件（`flowTodo.ftl`，Vue3 + Element Plus）

1. **SVG 流程进度图**（无 bpmn-js）：`<svg :viewBox>` 按 `nodeStatuses.length * 150` 计算宽度；`<line>` + `<marker>` 画带箭头连线；`<rect>` + `<text>` 画节点，颜色由 `nodeColor(status)` 映射（绿/蓝/橙/红/灰）；下方图例。待办行「进度图」按钮与审批弹窗内各渲染一份，共用 `progressData`。
2. **会签意见列表**：审批弹窗打开时并行拉 `/flow/state` 与 `/flow/countersign/opinions`，`el-table` 展示审批人/结果/意见/时间。
3. **会签投票**：弹窗内 `el-checkbox`「作为会签人投票」+ 模式下拉；勾选后「通过/驳回」改调 `flowCountersign(flowCode, bizId, [], mode, comment, approved)`，approvers 传空数组由后端取当前登录人。
4. **委派**：待办行新增「委派」按钮，弹窗填目标审批人 ID / 姓名 / 原因，提交 `flowDelegate`。
5. **内嵌设计器 tab**：节点卡片 `draggable="true"` + `dragstart/dragover/drop` 原生拖拽排序（也提供上移/下移按钮作为无鼠标拖拽时的兜底）；每节点可配 `from/to/节点名/审批角色/驳回目标/会签模式/会签人/条件分支`；右侧 JSON 双向绑定（`computed get/set`）；「校验」调 `/flow/def/validate` 并显示错误清单，「保存」先校验再调 `/flow/def/save`。

`flowApi.ftl` 新增函数：`getFlowProgress` / `flowCountersign` / `getFlowCountersignOpinions` / `flowDelegate` / `flowValidateDef` / `flowSaveDef`。**注意**：模板中不得出现裸 `${...}`（Freemarker 插值），现有 `task/{id}` 函数沿用 `${'$'}` 转义写法；新增函数全部用普通字符串拼接，无此问题。

## 六、流程设计器取舍（重点）

**方案 A（已交付）**：把简化设计器直接做进 `flowTodo.ftl` 的「流程设计」tab。
**方案 B（备选，已产出模板但未接线）**：独立 `flowDesigner.ftl` 单页。

选 A 作为当前产物里的实际交付，理由：

1. `GenTemplateEngine.renderFlowShared` 硬编码只 resolve `flowApi` / `flowTodo` 两个共享模板；新增共享模板必须在 `GenTemplateEngine` / `GenTemplateSeeder` 增加接线。本轮文件隔离**禁止修改**这两个类，因此独立模板无法输出到目标工程。
2. 内嵌 tab 与现有待办中心共用同一份 `@/api/flow` 与路由，零新增接线，开箱可用。
3. 独立模板保留为「可视化配置页」形态：它比纯 JSON textarea 更接近完整设计器（拖拽卡片 + 表单化审批人/条件配置 + JSON 预览 + 校验/保存），符合 backlog「流程设计器」诉求；`flowTodo.ftl` 内嵌版是同一能力的轻量副本。

**取舍代价与后续动作**：两台设计器代码存在少量重复；如需独立路由 `/flow/designer`，下版可在 `renderFlowShared` 增加一次 `resolveFromDb("flowDesigner")` 与 `pathPattern` 写盘，并把内嵌 tab 改为跳转链接，届时删除重复。该接线改动超出本轮允许文件范围，已列为未尽事项。

**为什么不引入 bpmn-js**：bpmn-js 体积大（依赖 diagram-js/diagram-js 布局与建模栈），与「轻量进度图」诉求不匹配；本方案只需展示**已有定义的节点状态**，无需编辑 BPMN XML，原生 SVG + 后端状态 JSON 足够，且产物零新增前端依赖。设计器也不生成 BPMN XML——保存只写 `sys_flow_def.nodes`，由 V6.1 既有 `GenBpmnBuilder` 在平台侧翻译/部署，避免产物侧重复实现 BPMN 语义。

## 七、零 diff 契约与验证方法

### 7.1 契约边界定义

流程能力包的**注入产物**是 `renderFlowShared` 的三个文件：`src/api/flow.js`、`src/views/flow/todo.vue`、`flow-router-snippet.txt`。其注入条件是「项目内任一表绑定 `flow_code`」（`GenTemplateEngine.renderFlowShared` 的 `flowBound` 计数）。

- **关闭态（无表绑定 flow_code）**：`renderFlowShared` 直接 `return Map.of()`，三个文件一个都不产出 → 新增的 API / 进度图 / 会签 / 委派 / 设计器代码全部不存在 → **产物零 diff**。
- **开启态（有表绑定 flow_code）**：按第五节产出，前后端端点可用。

后端 `FlowService` / `FlowController` / `FlowRecord` 等是 V6.1 明确「恒写」的 scaffold 基座（见 `GenScaffoldServiceImpl:290-308`，修 `controller.ftl` 引用断裂的历史决定），不属于能力包注入产物。本轮新增端点写在这些恒写基座里；关闭态下它们查询的 `sys_flow_def` / `sys_flow_task` 无数据，行为不变（接口存在但无副作用）。**若要求「整个产物字节级零 diff」**，需把新端点拆成独立产物并加能力包开关，涉及 `GenScaffoldServiceImpl` / `GenTemplateEngine` / DTO 改动，超出本轮文件隔离范围——这是本轮已知取舍，见第九节风险 R1。

### 7.2 验证方法（无需跑 mvn）

1. **静态门（本轮已做）**：
   - 新增/修改的 3 个 `.ftl` 用 `GenTemplateEngine.renderString(content, Map.of())` 的等价检查：模板内不得出现裸 `${`（Freemarker 会把 JS/Vue 文本当插值）或 `<#` 指令；已用 `grep` 核验，仅 `flowApi.ftl:33` 保留原有的 `${'$'}` 转义。
   - `ScaffoldFlowWriter.java` 4 个文本块括号平衡检查通过。
   - 基线测试 `GenTemplateBaselineTest.sharedEmpty` 会锁 `flowApi`/`flowTodo` 空模型快照——本轮内容变化是预期变化；中央统一验证时需按流程更新该基线并 review diff（本轮不改测试资源）。
2. **关闭态零 diff（推荐中央验证执行）**：
   - 取一个无 `flow_code` 绑定、无 `flow_engine` 的项目，用改动前后两版各生成一次产物，逐文件 `diff -r`（换行按 LF 归一，仓库 autocrlf 会制造平台噪声）。
   - 断言：不存在 `src/api/flow.js`、`src/views/flow/todo.vue`、`flow-router-snippet.txt` 三个文件；其余文件字节一致。
   - 后端恒写基座会多出新端点文本，按 7.1 的边界定义不计入能力包 diff；若 CI 要求全产物零 diff，需按下版计划补齐接线后再断言。
3. **开启态功能验证（中央统一验证执行）**：
   - 建 `hr_leave_flow`（3 节点，`manager` 角色，节点 2 配 `approvers:[2,3], countersignMode:ALL`），绑定业务表并生成产物。
   - 提交单据 → 待办可见 → 打开审批弹窗：SVG 进度图有 3 个节点且第 2 个为蓝色 `CURRENT`；会签区初始为空。
   - 两名会签人分别投票同意 → `/flow/records` 出现两条 `COUNTERSIGN_AGREE` 与一条 `COUNTERSIGN_RESULT`，业务状态推进；反对票一票 → 状态回 `rejectTo`。
   - 委派：填 ID 2 → 记录出现 `DELEGATE` + `DELEGATE_ASSIGN`，进度图该节点显示橙色 `DELEGATED`。
   - 设计器：加节点、拖拽排序、改角色与条件、校验通过、保存 → 重新打开 `/flow/state` 见新节点定义。
4. **编译门**：本轮按要求不跑 `mvn`；生成物 Java 字符串由中央统一验证编译（`FlowService` default 方法 + 两实现 override，理论上编译安全；重点看 `TypeReference<>` 推断与 `instanceof` 模式匹配需 Java 17+，产物目标 Java 21 满足）。

## 九、未尽事项与风险

| 编号 | 事项 | 影响 / 建议 |
|---|---|---|
| R1 | 严格「整个产物字节级零 diff」未覆盖后端恒写基座 | 新端点文本进入所有产物的 `FlowService`/`FlowController`/`BuiltinFlowService`。需下版把新端点拆成受能力包开关控制的独立产物（改 `GenScaffoldServiceImpl`/`GenTemplateEngine`/DTO），本轮文件隔离不允许 |

| R3 | 会签轮次隔离简化 | 判定按「当前 `from_status` 下的全部历史票」统计；同一节点多次驳回重审后，旧轮次票可能混入。下版可在节点定义里加轮次 token（如 `roundId`）或用 `oper_time > 上次流转时间` 过滤 |
| R4 | builtin 引擎委派后待办可见性 | builtin `todo()` 按角色匹配，不按 `assignee_id`；委派只留痕与改状态展示，目标人若角色不符仍看不到待办。activiti 走 `setAssignee` 可见。下版给 builtin `todo()` 加 `DELEGATE_ASSIGN` 并集 |
| R5 | 条件分支仅配置不执行 | 设计器可写 `condition` 字段并随定义保存，但 builtin 流转仍按节点顺序；条件判断由平台 `GenBpmnBuilder` 翻译到 BPMN 网关后（activiti 引擎）才生效。轻量设计器不编辑 BPMN XML |
| R6 | 基线快照需更新 | `GenTemplateBaselineTest.sharedEmpty` 锁 `flowApi`/`flowTodo` 空模型产物，本轮内容变化会让该用例变红；按项目规则由中央统一验证更新基线并 review |
| R7 | 未跑编译与端到端 | 按要求不跑 mvn；生成物 Java 字符串、Vue SFC 未经真实编译/浏览器验证，风险集中在 `TypeReference<>` 推断、activiti API、SVG 模板渲染 |
| R8 | 新端点未进生成物权限豁免清单 | `ScaffoldAuthWriter.flowApiPermsJava` 只映射了既有 7 个 `/flow/*` 端点；生成的 `PermissionChecker` 对**未映射写端点 fail-closed**，因此开鉴权的产品里非 admin 用户调用 `POST /flow/countersign`、`/flow/delegate`、`/flow/def/validate`、`/flow/def/save` 会 403（admin 的 `*:*:*` 直通不受影响）。本轮禁止改 `ScaffoldAuthWriter.java`，未修。下版在该贡献者里补 4 条 `"POST /flow/xxx" -> ""`（仅登录即可，与既有 flow 端点同策略）即可 |
